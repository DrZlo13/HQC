# hqc — техническое задание

Версия 0.23, 2026-10-24. Статус: согласованная архитектура после шести ревью и обзора
аналогов (§22), до начала реализации. Изменения — в §23, старые версии —
в `SPEC-CHANGELOG.md`. Пометки: **[решение]** — принято, требует подтверждения;
**[проверить]** — требует проверки на реальной сборке.

Термины: **ход** — один цикл «ввод → работа агента → финальный ответ», начинается
событием `user.message` или `peer.message` с `mode=ask` и заканчивается
`agent.message` с `final: true`. **Голая модель** — LLM без доступа к файловой
системе. **Подхват** — продолжение (resume) сессии в другом месте: с VS Code на hqc
или обратно. **Hermes** — Hermes Agent от Nous Research; на llm-server работает как
демон (messaging-гейтвей) и дополнительно умеет запускаться отдельным процессом как
ACP-сервер (`hermes acp`). **ACP** — Agent Client Protocol (Zed), JSON-RPC по stdio
между клиентом и агентом: `initialize`, `session/new`, `session/prompt`,
`session/update`, `session/request_permission`, `session/cancel`, `session/load`.
**Владелец воркера** — пользователь, зарегистрировавший машину. **Владелец
сессии** — пользователь, создавший сессию.

## 1. Цель и границы

hqc — единый интерфейс для ведения проектов с LLM-агентами с любого устройства.
Агенты физически работают на разных машинах и разных ОС, пользователь общается с ними
через веб-клиент, похожий на Discord: проекты, внутри проектов сессии, в сессии агент.

Что hqc делает:

- хранит проекты, сессии и полную историю событий в одном месте;
- запускает и ведёт агентов на той машине, где лежит код и подключено железо;
- показывает сессии, начатые в VS Code, и позволяет подхватить их с телефона;
- даёт агентам инструменты для обмена сообщениями, артефактами и запросами друг к другу;
- пускает коллег как отдельных пользователей с явным шарингом.

Что hqc не делает:

- не реализует агентный цикл для Claude Code и ACP-агентов: цикл живёт в рантайме.
  Для голой модели хаб крутит минимальный цикл «модель ↔ MCP-инструменты hqc» (§8.3);
- не дублирует возможности Hermes (крон задач агента, kanban, память, Telegram);
- не является IDE: нет редактора файлов, диффы только как артефакт;
- не даёт жёсткой изоляции между сессиями на одной машине без контейнера или
  отдельного пользователя ОС (§14).

## 2. Топология

**Hub** — один всегда доступный сервис. Хранит состояние, маршрутизует события, отдаёт
API клиентам и воркерам. Исполняет только голые модели (§8.3).

**Worker** — демон на каждой машине, где должны работать агенты. Подключается к хабу
только наружу по WebSocket. Внутри: нативный адаптер Claude Code, общий ACP-адаптер
для Hermes и любых агентов из ACP-реестра, MCP-сервер hqc, зеркало сессий VS Code,
операции с workspace, локальный конфиг с ограничениями и окружениями.

**Client** — веб-приложение, позже Tauri и мобильное. Общается только с хабом.

Размещение: хаб в домашней DMZ за Cloudflare Tunnel. Люди входят через Cloudflare
Access (SSO), воркеры — через отдельный маршрут с собственными токенами (§6, §20).

### 2.1 Модель угроз

- Воркер не доверяет хабу в части `allowed_roots`, окружений, привязок и
  `allow_foreign_sessions`; идентичность пользователя и ответы на разрешения приходят от
  хаба и ему доверяются **[решение]**. Хаб — корень доверия для переписки и разрешений:
  кто контролирует хаб, может ответить `allow` на любой `approval.request`, писать в любые
  сессии и выдать любую сессию за сессию владельца воркера (`owner_is_worker_owner`).
- Последствия компрометации хаба: удалённое выполнение кода на каждом подключённом
  воркере от имени его владельца в пределах `allowed_roots` и того, что разрешают
  инструменты агента (Bash может выйти за пределы workspace), — хаб стартует сессию, шлёт
  ввод и сам отвечает `once` на запрос разрешения; плюс чтение всей переписки, транскриптов
  в событиях и push-подписок. Защита — сам хаб: Access, только туннель, без открытых
  портов (§20). Подпись ввода и ответов ключами устройств, зарегистрированными на воркере
  локально, — итерация 3+.
- Хаб **не** может: выйти за `allowed_roots` воркера, выбрать окружение или профиль
  Hermes для пути, которые владелец воркера не привязал локально, включить
  MCP-серверы с машины. Это задаётся только локальным конфигом воркера (§14); воркер
  игнорирует расходящиеся значения из `session.start` и отвечает ошибкой.
- Обещание про локальные MCP держится для Claude Code (`--strict-mcp-config`)
  и Hermes (`HERMES_ACP_SKIP_CONFIGURED_MCP=1`, воркер ставит всегда). Для других
  ACP-агентов общего способа нет: в локальном конфиге каждый `acp_agent` объявляет
  `isolation: verified | none`; агент с `none` не допускается в чужие сессии
  (§11.1) и обещание на него не распространяется.
- Воркер — удалённое выполнение кода на машине владельца. Любой, кто может писать
  в сессию на этом воркере, выполняет код от имени владельца в пределах его политики.
- Между сессиями одного воркера граница мягкая (§14): процессы работают от одного
  пользователя ОС и могут читать окружение и файлы друг друга.
- Коллега с доступом к расшаренному проекту ограничен грантами (§11) и подтверждениями
  владельца воркера (§10).

## 3. Модель данных

Все сущности имеют `id` (uuid v7), `created_at`, `updated_at`. `owner_id` есть у Worker,
Project, Workspace, Session, Artifact, Grant, ScheduledMessage. У Event владельца нет,
есть `author`.

### User
`email` (из проверенного JWT Cloudflare Access), `display_name`, `api_keys`
(OpenRouter, Anthropic API; шифруются мастер-ключом хаба, который лежит в env/файле
хаба, не в базе), `timezone`, `personal_project_id` (неявный личный проект, создаётся
при первом входе; в нём живёт персональная сессия-ассистент).

### Worker
`owner_id`, `name`, `os`, `token_hash`, `status` (online/offline), `last_seen`,
`protocol_version`, `boot_id` (из последнего `hello`, §5.2), `capabilities` (`claude_code: {version, sessions_registry?}`, `acp_agents[{name,
version, load_session, resume, image, isolation}]` — результат `initialize` каждого
агента при старте воркера), `local_models[]`, `share_local_models`, `allowed_roots[]`,
`environments[]` (имена), `env_bindings[]` (путь → окружение, профиль Hermes),
`allow_foreign_sessions`, `idle_timeout`, `system_session_id` (§10.2), `machine_hash` (с 0.23:
отпечаток машины из регистрации и последнего `hello`, §5.1; в объект воркера API не входит).

`system_session_id` — служебная сессия воркера (§10.2). Создаётся вместе с воркером при
подтверждении регистрации (`POST /api/workers/enroll/confirm`), воркерам до 0.17 — миграцией
хаба `0006`, а если её всё же нет — на `hello`. Хаб сообщает её воркеру в `hello.ack`
(`system_session_id`); `GET /api/workers` отдаёт её в объекте воркера. Отзыв воркера сессию
не удаляет, а архивирует (история остаётся, §10.2); регистрация с заменой (§5.1)
разархивирует её, удаление отозванного воркера (§6) удаляет её вместе с воркером.

Регистрация с заменой (§5.1) оставляет воркеру его `id`: `name`, `os` и `token_hash` берутся
у новой регистрации, `revoked_at` и `boot_id` сбрасываются; сессии, workspace и служебная
сессия остаются на этом `id`.

Поля `allowed_roots`, `environments`, `env_bindings`, `allow_foreign_sessions`,
`share_local_models`, `acp_agents` — **источник истины в локальном конфиге воркера**;
хаб хранит копию из `hello` для отображения и ранней валидации.

### Project
`owner_id`, `name` (1–100 символов), `slug` (уникален у владельца, не меняется при
переименовании), `description`, `default_workspace_id` (nullable),
`session_template` (§13.3), `is_personal`. Первый workspace проекта становится его
`default_workspace_id`; при удалении default-workspace им становится самый ранний из
оставшихся. Личный проект (`is_personal`) нельзя удалить и переименовать (`409
personal_project`), остальные поля меняются; новых проектов можно создавать сколько угодно.
Удаление проекта удаляет его workspace-записи и сессии (с событиями, как §17.4), процессам
агентов уходит `session.kill`; папки и транскрипты на воркерах не трогаются.

### Workspace
`project_id`, `worker_id`, `path`, `label`, `environment` (имя; отображение привязки
из локального конфига воркера), `ephemeral`, `created_by_hqc`, `kind`
(dir/clone/worktree), `origin_workspace_id`, `mirror_enabled` (с 0.23 по умолчанию `true`: зеркало
сессий Claude Code включено у всех workspace, переключатель — `PATCH`, §6, §9.2).
Workspace — **логическая** граница: все операции hqc (cwd сессий, inbox, зеркало,
удаление) ограничены его путём. Принудительной изоляции файловой системы он не даёт.
Workspace — объект хаба **[решение]**: воркер о нём знает только то, что его путь лежит
внутри `allowed_roots` (проверяет при `fs.stat` и при каждом `session.start`, §5.3).
`path` — канонический путь, который вернул воркер на `fs.stat` (симлинки раскрыты).
Папка принадлежит ровно одному проекту: на одном воркере пути workspace уникальны и не
вложены друг в друга (сравнение по компонентам пути: `/a/b` и `/a/bc` не пересекаются);
новый путь, который совпадает с существующим workspace, лежит внутри или содержит его, —
`409 workspace_conflict` (§6). На разных воркерах один и тот же путь — разные папки.

### Session
`project_id`, `owner_id`, `workspace_id` (nullable; с 0.16 обязателен при создании —
сессии без workspace §8.4 через API пока не создаются; без workspace — только служебная
сессия воркера, §10.2), `worker_id` (воркер workspace;
обязателен для Claude Code без workspace; для голой модели null; ACP-агенты без workspace
не допускаются, §8.4), `cwd` (относительный путь внутри workspace, по умолчанию `.`),
`title`, `title_source` (`default` | `runtime` | `user` — кто поставил заголовок), `slug`
(уникален в проекте, не меняется при переименовании), `agent`,
`auto_approve`, `wake_on_send` (по умолчанию false), `locked_by` (none/hqc/vscode),
`last_seq`, `archived`, `vscode_active_at` (nullable; когда хаб последний раз получил
событие зеркала с `recent` — запись в файл за последние 30 с; по нему считается тишина для
подхвата без данных реестра, §9.3; в объект сессии API не входит), `held_by` (nullable
`{entrypoint, status}`: живой процесс Claude Code вне hqc, у которого транскрипт сессии открыт,
по реестру живых сессий на воркере, §9.3; в объекте сессии API и в `session.summary` — поле
`held_by?`), `vscode_held_at` (nullable; с какого момента транскрипт держат; в объект сессии
API не входит), `system` (bool: служебная сессия воркера,
§10.2; в объекте сессии API — только `system: true`). `state` и `queue_len` (§17.1) **не хранятся**, вычисляются
хабом при отдаче. В первой версии в сессии ровно один агент; доступ людей к сессии
определяется только Grant.

Заголовок: создание без `title` даёт «Сессия N» (N — номер сессии по порядку в проекте,
считая архивные; `slug` — `session-N`) с `title_source: default`; `title` при создании и
`PATCH title` ставят `user`. Заголовок от рантайма (`session.state.title`, §5.4; у Claude
Code — `ai-title`, §8.1) хаб применяет и ставит `runtime`, только если `title_source` не
`user`: переименованную пользователем сессию рантайм не переименовывает.

Заголовок от хаба (с 0.23, T21). После первого финального `agent.message` сессии с `title_source:
default` (от воркера или из зеркала: импортированная сессия — так же, по первым записям) хаб в
фоне просит модель заголовков (`HQC_TITLE_MODEL = "<provider>:<model>"`, provider `anthropic` —
Messages API или `openai` — любой OpenAI-совместимый, в том числе OpenRouter и локальная модель;
база `HQC_TITLE_BASE_URL`, ключ `HQC_TITLE_API_KEY`, может отсутствовать) дать заголовок до 60
символов на языке пользователя по первому сообщению и первому ответу (каждый обрезан до 2000
символов). Ошибка и таймаут 15 с — только в лог. Без модели или при ошибке заголовок — первая
непустая строка первого промпта без разметки Markdown, обрезанная по слову до 60 символов с «…».
Заголовок ставится с `title_source: runtime` и только поверх `default`: заголовок пользователя
или рантайма (`ai-title`), пришедший раньше, не перезаписывается; позже пришедший `ai-title`
заменяет его по общему правилу. Один вызов модели на сессию за процесс хаба. Модель — тот же
модуль хаба (`llm`, один метод `complete(system, user, max_tokens)`), что понадобится голой модели
итерации 4 (§8.3).

Зеркало (§9): `locked_by` — кто ведёт сессию: `hqc` — процесс воркера (с подхвата или первого
ввода до его остановки), `vscode` — чужой держатель или писатель транскрипта (VS Code, `claude`
в терминале), `none` — никто. Сессия, созданная зеркалом, получает `runtime_session_id` = uuid файла, `cwd`
из записи относительно workspace, заголовок из `ai-title` (`title_source: runtime`) или «Сессия
N», `locked_by` по §9.1. Ищется по паре (`worker_id`, `runtime_session_id`).

### Agent (встроен в Session)
`runtime` (claude_code / acp / bare / none; `none` — только у служебной сессии воркера:
агента нет, процесс не стартует, §10.2), `acp_agent` (имя агента из локального конфига
воркера для `acp`), `model`, `runtime_session_id` (строка: uuid jsonl у Claude Code,
произвольный id у ACP-агентов), `process_state`
(stopped/starting/running/stopping), `system_prompt`, `disallowed_tools[]`,
`restricted` (§8.4), `start_failures` (счётчик, §5.2). Смена рантайма между ходами
означает **новую сессию рантайма с пустым контекстом**: `runtime_session_id`
сбрасывается, история hqc остаётся, пользователю предлагается пересказ
последних N сообщений стартовым промптом.

### Event
`session_id`, `event_id` (uuid; для событий, порождённых записями jsonl Claude Code —
и адаптером, и зеркалом, и импортом — это uuid v5 от `uuid` записи, поэтому один
и тот же факт из двух источников даёт один `event_id`; если в записи несколько блоков
контента, блок 0 получает v5 от `uuid`, блок `i > 0` — v5 от строки `"<uuid>/<i>"`
в том же пространстве имён, правило обязательно для всех трёх источников (§9.2);
для остальных — v7 от отправителя), `seq` (назначает хаб, монотонный в сессии), `ts`, `author`
(`{kind: user|agent, id}` или `{kind: system}` без `id`; для агента `id` = его
`session_id`), `type`, `payload`, `chain` (`{chain_id, depth, hops}` для цепочек
агент→агент, иначе null), `client_op_id` (эхо для клиента), `delivery` и
`delivered_at` — два плоских поля события, только у `user.message` и `peer.message`:
`delivery` ∈ `pending | delivered | failed`, `delivered_at` — время доставки.

### ReadCursor
`user_id`, `session_id`, `last_read_seq`. Источник «непрочитанного» (правило — §6).

### Artifact
`owner_id`, `session_id` (первая сессия, во вводе которой артефакт пришёл; null до этого),
`kind` (file/image/diff/html/text), `mime`, `size`, `sha256`, `name` (последний компонент
пути без управляющих символов, до 255 байт), `storage_key` (= `sha256`: содержимое на
диске общее для всех записей с тем же хэшем). Запись уникальна по `(owner_id, sha256,
name)`: тот же файл тем же пользователем под тем же именем — та же запись. Какие сессии
получили артефакт во вводе, хаб помнит отдельно: их воркерам он отдаётся (§5.3, §12).
События ссылаются только на `artifact_id`; ссылки на скачивание выдаются при рендере
(§12). Неиспользуемые артефакты удаляет уборка хаба (с 0.23, §12); `updated_at` — последняя
загрузка того же файла или ввод с ним.

### Grant
`owner_id` (кто выдал), `resource_type` (project/session), `resource_id`, `user_id`,
`level` (view/write/manage).

### PendingRequest
Открытые запросы, переживающие перезапуск хаба: `kind`
(approval/clarify/ask/worker_approval/mcp_call), `session_id`, `request_id`,
`payload`, `expires_at`, `from_session_id`, `from_event_id`, `worker_id`
(для ask и mcp_call: кому отдать результат), `result` (заполняется, когда ответ
получен, но ещё не доставлен воркеру).

### ScheduledMessage
`owner_id`, `session_id` или (`project_id`, `workspace_id`, шаблон), `cron` или `at`,
`timezone`, `message`, `enabled`, `last_run`, `catch_up`.

## 4. Схема событий

Единая схема для всех рантаймов. Адаптер переводит поток рантайма в эти события,
клиент рендерит только их. Колонка «источник» — компонент, который производит событие;
`author` задаётся по §3. `?` — необязательное поле: отсутствует, если значения нет
(`null` читается так же).

| type | payload | источник |
|---|---|---|
| `user.message` | `text`, `artifact_ids[]` | клиент; зеркало — промпты из транскрипта Claude Code (§9.1) |
| `agent.delta` | `text` | адаптер; только транспорт, в базу не пишется |
| `agent.message` | `text`, `final`, `in_reply_to?` (event_id ввода, начавшего ход) | адаптер. `final: true` — конец хода; `final: false` — текст между вызовами инструментов |
| `agent.thinking` | `text` | адаптер, если рантайм отдаёт |
| `tool.call` | `call_id`, `tool`, `args_preview` | адаптер |
| `tool.result` | `call_id`, `result_preview`, `error` (bool), `error_text?` (краткий текст ошибки), `duration_ms?`, `artifact_id?` (дифф или большой результат, §12) | адаптер |
| `approval.request` | `request_id`, `tool`, `description`, `options[{id, label, canonical}]`, `expires_at?`, `policy_hint?` (allow/deny) | адаптер; `options` — **реальные варианты агента**, `canonical` ∈ once/session/always/deny/deny_always для кнопок клиента; `policy_hint` — вызов подходит под правило `allow` или `deny` блока `[permissions]` воркера (§14), нет поля — не подходит ни под одно; клиент подписывает им карточку |

| `turn_lost` | хаб | ход потерян: процесс агента остановился посреди хода, воркер перезапустился или от воркера долго нет событий хода (сторожевой таймер, «no events for N s»; §17.3) |

Правила:

- События терпимые: неизвестные поля в `payload` игнорируются; событие неизвестного
  `type` разбирается как «неизвестное» и хранится и пересылается как есть, клиенты его
  не рендерят, но не падают; неизвестное значение перечисления внутри события
  (`state`, `canonical`, `mode`, `kind`, `reason`, `policy_hint`) читается как «неизвестное». Событие
  известного `type` с неверным `payload` — ошибка.

- Файлы пользователя всегда идут в `user.message.artifact_ids[]`, в том числе без текста
  (`text` пустой): это ввод, и агент их получает (§8.1, §12) **[решение]** (T16). Событие
  `attachment` агенту не доставляется — это файл, показанный в ленте (`hqc_attach`,
  итерация 3); клиент своих `attachment` не пишет.
- `*_preview` обрезаются воркером до 4 КБ; полный результат инструмента в хаб
  не передаётся, кроме диффов и результатов, сохранённых артефактом.
- `agent.delta` идёт клиентам по WebSocket и не сохраняется; сохраняется `agent.message`.
- История не переписывается. Защита от подделки заголовка peer-сообщений делается
  при доставке в рантайм (§7.1).

## 5. Протокол Worker ↔ Hub

Транспорт: одно постоянное WebSocket-соединение от воркера к хабу, JSON-фреймы,
heartbeat 20 с, переподключение с экспоненциальной задержкой.

Каждый фрейм: `{id, type, payload}`. Ответ на фрейм-запрос:
`{id, type: "ack"|"result"|"error", payload}` с тем же `id` (на `hello` — `hello.ack`
или `error`). Поля с `?` — как в §4.

- `ack` {event_id?, seq?}: на `event` — `{event_id, seq}` (§5.2), на `session.input` —
  `{event_id}` доставленного ввода, в остальных случаях пустой `{}`.
- `error` {code, message, retryable, details?}. Начальный список `code`:
  `protocol_version_unsupported` (`details: {min_version}`), `unauthorized`,
  `unknown_session`, `invalid_frame`, `agent_start_failed`, `internal`, `locked_vscode`
  (ответ воркера на `session.input` сессии, которую он отпустил, §9.3). Коды — строки,
  список открытый; неизвестный код обрабатывается как `internal`.

### 5.1 Регистрация и версия
URL хаба у воркера (`hub_url` в `worker.toml` и аргумент `enroll`) — только `https://`;
`http://` допускается для loopback-хостов (`localhost`, `127.0.0.0/8`, `[::1]`) или при
явном `insecure_http = true` в `worker.toml` (у `enroll` — флаг `--insecure-http`), иначе
воркер не стартует: токен и `poll_token` иначе шли бы открытым текстом. HTTP-клиент
`enroll` не следует редиректам (тело с `poll_token` не уходит на другой адрес).

`hqc-worker enroll <hub-url>` печатает код и готовую ссылку
`<hub-url>/#/enroll?code=XXXX-XXXX` (экран подтверждения клиента с подставленным кодом),
пользователь подтверждает код в вебе под своим логином, воркер получает долгоживущий
токен. Хранение токена: на macOS — Keychain (generic password, service `hqc-worker`,
account = URL хаба); на других ОС в первой версии — файл `$HQC_HOME/token` с правами 0600
(каталог 0700, запись через временный файл и rename); libsecret и DPAPI — позже.
Токен отзывается из UI. В `hello` воркер шлёт
`protocol_version`; хаб отвечает `hello.ack {protocol_version, worker_id, server_time,
system_session_id?}` (служебная сессия воркера, §10.2)
или `error {code: protocol_version_unsupported, details: {min_version}}`. Версию хаб
проверяет до строгого разбора `hello`: `hello` другой версии может иметь другую форму,
но всё равно должен получить `protocol_version_unsupported`, а не `invalid_frame`. При
несовместимости воркер пишет в лог и в трей «нужно обновление», повторяет попытку
раз в час и не делает ничего другого; обновление — руками или `hqc-worker update`.

Регистрация по HTTP (маршрут `/worker/*`, без Access, с rate limit; тела —
`hqc_proto::api`, примеры `examples/wire/api.enroll*.json`):
- `POST /worker/enroll {name, os, protocol_version}` → `{code, poll_token, expires_at,
  poll_interval_s}`; `protocol_version` справочный (решает `hello`), неизвестные поля
  тела хаб игнорирует; `code` — 8 символов `XXXX-XXXX` без похожих букв, живёт 10 минут;
  `poll_token` — секрет воркера, передаётся только в теле (не в URL), в базе только хэш.
  Хаб сохраняет при коде `CF-IPCountry` и адрес запроса (лимиты, §20).
- Пользователь вводит код в вебе. Сначала `GET /api/workers/enroll/{code}` →
  `{name, os, created_at, country?, replaceable?}` (404 — нет такого живого кода): клиент
  показывает имя, ОС, время и страну, и кнопка подтверждения активна только после их
  загрузки — ссылку с кодом мог прислать кто-то другой. Затем `POST
  /api/workers/enroll/confirm {code, name?, replace_worker_id?}` → `{worker_id, name,
  replaced?}`; регистр и дефис в коде не важны. Поиск кода (оба запроса) — не больше 30
  в минуту на пользователя.
- Воркер опрашивает `POST /worker/enroll/poll {poll_token}` → `{status: pending}`,
  `{status: confirmed, worker_id, token, replaced?}` (токен выдаётся ровно один раз, в базе
  только хэш) или `{status: expired}`.
- `/worker/ws` — заголовок `Authorization: Bearer <token>`; неизвестный или отозванный
  токен — 401 до апгрейда, отзыв между апгрейдом и `hello` — `error {unauthorized}` на
  `hello` и закрытие. `DELETE /api/workers/{id}` отзывает токен, рвёт соединение и
  архивирует служебную сессию воркера с `system worker_revoked` (§10.2).

**Регистрация с заменой** (с 0.21). Повторный `enroll` той же машины (новый бинарник, другое
хранилище токена, отозванный токен) иначе дал бы новый `worker_id`, а сессии, workspace и
служебная сессия остались бы на старом, навсегда офлайн. Поэтому `replaceable[]` в ответе
`GET /api/workers/enroll/{code}` — воркеры пользователя, которые сейчас не на связи или
отозваны: `{id, name, os, status: offline|revoked, last_seen?, sessions_count}`
(`sessions_count` — неархивные сессии на воркере, без служебной); пусто — поля нет. Клиент
предлагает «это та же машина, заменить <имя>» (по умолчанию — новый воркер). С
`replace_worker_id` хаб при подтверждении:
- проверяет, что воркер принадлежит пользователю (иначе `400`), и что он не на связи (`409
  worker_online`; отозванный воркер на связи не считается); пока другой подтверждённый, но
  не забранный опросом код уже заменяет этот воркер, — `409 conflict`. Отказ код не тратит;
- новой записи не создаёт: код получает этот `worker_id`; старый токен перестаёт работать
  сразу (`token_hash` сбрасывается, оставшееся соединение рвётся), `name` (из `name?` или
  присланного воркером) и `os` — новой регистрации, `revoked_at` снимается, `boot_id`
  сбрасывается (первый `hello` нового процесса — перезапуск, §5.2);
- служебная сессия остаётся (разархивируется и получает новое имя заголовком), в неё пишется
  `system {code: worker_replaced, old_name, new_name}`; сессии и workspace не меняются;
- в ответе `replaced` — прежнее имя воркера. Новый токен записывается на этот `worker_id`
  при опросе; ответ опроса несёт тот же `replaced`, `hqc-worker enroll` печатает «Enrolled as
  worker <id> (replaced <имя>)».

Подтверждение замены — то же решение владельца, что и обычная регистрация: воркер,
которого заменили по чужой ссылке, получил бы сессии заменённого. Поэтому клиент
показывает замену явным выбором с именем и числом сессий, а не галочкой по умолчанию.

**Отпечаток машины** (с 0.23, T21). Воркер шлёт `machine_id` в `POST /worker/enroll` и в каждом
`hello` (поле необязательное, у старых воркеров его нет): стабильный идентификатор машины —
macOS `IOPlatformUUID` (`ioreg`), Linux `/etc/machine-id`, Windows `MachineGuid` из реестра, иначе
случайный, сохранённый в `$HQC_HOME/machine_id`, — хэшированный sha256 с солью `hqc` (64
шестнадцатеричных знака); сам идентификатор с машины не уходит. Хаб хранит его у кода регистрации
и у воркера (`machine_hash`; значение не той формы игнорирует); существующие воркеры получают его
с первым `hello` после обновления, замена — от новой регистрации. В `replaceable[]` воркеры с тем
же `machine_hash`, что у кода, идут первыми и помечены `same_machine: true` (поле передаётся
только `true`); клиент предвыбирает замену такого воркера, «Новый воркер» остаётся выбором.
Отпечаток — подсказка, а не проверка: он не мешает заменить другой воркер и не заменяет
подтверждение владельца.

### 5.2 Гарантии доставки
Worker → hub:
- Воркер ведёт **outbox** на диске: событие сначала пишется в outbox, потом отправляется.
  Через outbox идут `event`, `mirror.event`, отчёты о держателе (`session.state` с nil
  `session_id`, §5.4, §9.3), `mcp.call`.
- Хаб отвечает `ack {event_id, seq}`; до ack воркер повторяет после переподключения.
- Дубли отбрасываются по `event_id` (уникальный индекс) и получают `ack` с `seq` уже
  сохранённого события. События для сессий, которых хаб не знает (удалены), получают
  `ack` с `seq: null` (поле может и отсутствовать) и отбрасываются.
- Фреймы worker ↔ hub строгие: версия согласована в `hello`, фрейм неизвестного `type`
  или с неверным `payload` получает `error {code: invalid_frame}`. Терпимость к
  неизвестному — только внутри событий (§4): хаб сохраняет событие неизвестного
  `type` как есть.
- Хаб хранит `payload` события в том виде, в каком получил (`jsonb` как есть), и отдаёт
  клиентам тот же сырой JSON; типизированный разбор — только для логики хаба, обратно
  в хранилище из типов ничего не сериализуется, поэтому значения от более нового
  воркера не теряются. Исключение — U+0000, который Postgres не принимает ни в `jsonb`,
  ни в `text`: хаб заменяет его на U+FFFD во всех строках и ключах входящего фрейма
  воркера до разбора, а также в событиях, которые пишет сам (ввод клиента, ответы),
  и в `title` сессии. Воркер делает ту же замену у источника: адаптер Claude Code — во
  всех текстах событий (`result_preview`, `error_text`, `args_preview`, `description`,
  `agent.message`, `agent.delta`, `agent.thinking`, вопросы `clarify.request`).
- Событие, которое база отвергла из-за самих данных (ошибка кодировки, значение вне
  диапазона, слишком длинное поле: SQLSTATE классов 22, 23, 54), получает
  `error {code: invalid_frame, retryable: false}` и воркером выбрасывается; ошибка
  соединения с базой и прочие — `error {code: internal, retryable: true}`.
- `error` с `retryable: true` на `event` оставляет событие в outbox до следующего
  соединения; воркер считает такие ответы на каждое событие (счётчик в outbox) и после
  **10** пишет `error` в лог и удаляет событие, чтобы оно не переотправлялось вечно.
- `seq` назначает хаб; клиенты видят только события с `seq`.
- `agent.delta` в outbox не пишется и при обрыве теряется, это допустимо. Идёт тем же
  фреймом `event`; хаб отвечает `ack {event_id}` без `seq` и не сохраняет его.
- `ack` на `session.input` и `agent.delta` идут мимо outbox, а события хода — через него,
  поэтому хаб может получить `ack` ввода и дельты позже `tool.call`/`approval.request`
  того же хода. Хаб не полагается на порядок между ними (проверено на адаптере T4):
  `ack` ввода, пришедший после `agent.message` с `final: true` и `in_reply_to` этого
  ввода, ход заново не открывает. Ход, закончившийся без финального текста (только
  `status idle|error`), при таком опоздании `ack` остаётся «идущим» до следующего хода
  **[проверить]**.
- Событие для сессии чужого воркера обрабатывается как для неизвестной: `ack` без `seq`.

Hub → worker:
- `user.message` и `peer.message` хаб хранит с `delivery: pending` и шлёт как
  `session.input`. Воркер отвечает `ack {event_id}` после передачи ввода в рантайм (Claude Code —
  после эха `--replay-user-messages`; ACP — после отправки `session/prompt`). После
  `hello` хаб шлёт `session.start` с `mode: resume` каждой сессии этого воркера, у которой
  есть `pending` ввод, открытый `approval`/`clarify` или ответ на запрос, ещё не
  подтверждённый воркером; после `ack` на него — неподтверждённые ответы, затем
  `pending` вводы в порядке `seq`. Воркер на ввод сессии, для которой в его процессе не
  было `session.start`, отвечает `error {code: unknown_session, retryable: true}`.
- Если процесс агента не стартует (нет бинарника, профиль не настроен), воркер
  отвечает `error {retryable: true}`; после **3 неудачных стартов** подряд хаб ставит
  вводу `delivery: failed`, пишет `system` с причиной, сессия переходит в `error`;
  кнопка «повторить» сбрасывает счётчик и возвращает ввод в `pending`.
- На каждом соединении хаб шлёт `session.start` до первого `session.input` сессии
  и досылает вводы только после `ack` на него; `session.state {process_state: stopped}`
  сбрасывает это, и следующий ввод снова начинается с `session.start`. `mode` в
  `session.start` (§5.3): `new`, если хаб ещё ни разу не отправлял `session.start` этой
  сессии, иначе `resume`. `session.start` для живого процесса воркер подтверждает `ack`,
  не трогая процесс. Ответ `error`
  на `session.input` с `retryable: true` или кодом `agent_start_failed` считается
  неудачным стартом; иная ошибка помечает этот ввод `failed` (`system` с кодом
  `input_rejected`). Неудачный старт повторяется через паузу, пока есть `pending`
  вводы. После третьего подряд все `pending` вводы сессии становятся `failed`,
  пишется `system` с кодом `agent_start_failed`. Новый ввод после этого получает одну
  попытку старта; «повторить» (`POST /retry`) обнуляет счётчик.
- Очередь ввода воркера (§17.2) в памяти; источник истины — `pending` события
  в хабе, перезапуск воркера их не теряет.
- Перезапуск воркера хаб узнаёт по `boot_id` в `hello` (§5.4): воркер генерирует его
  при старте процесса, хаб хранит последний. Новый `boot_id` — перезапуск (§17.3):
  открытые `approval`/`clarify` сессий воркера отменяются с `worker_restart` (только
  событие: ни один процесс запрос уже не держит, фрейм `deny` не шлётся), ответы,
  которые воркер не подтвердил, отбрасываются, незакрытый ход получает `system` с кодом
  `turn_lost`, `process_state` сессий становится `stopped`. Тот же `boot_id` — обрыв
  связи: хаб ничего не отменяет, процесс и его запросы живы **[решение]**.
- Смещения зеркала по каждому файлу jsonl и кэш «файл → cwd» воркер хранит на диске.

MCP-вызовы (worker → hub → worker):
- `mcp.call {request_id, session_token, tool, args}` → `mcp.result {request_id,
  result | error}`. Быстрые инструменты (`attach`, `list`, `search`, `schedule`, `send`,
  `spawn`) отвечаются сразу. `ask` — отложенный: хаб создаёт `PendingRequest`
  с `worker_id` и отвечает `mcp.result` только когда пришёл ответ или истёк таймаут.
  Если в этот момент воркер офлайн, результат ждёт в `PendingRequest.result`
  и досылается после `hello`; воркер, у которого блокирующего вызова уже нет
  (перезапустился), отвечает `ack` и отбрасывает.
- `mcp.cancel {request_id, reason}` — воркер сообщает, что отложенный вызов умер на его
  стороне (§7.2). Получив его, хаб закрывает `PendingRequest` с ошибкой и пишет в
  сессию-отправитель событие `system` с кодом `ask_cancelled`; целевой сессии ничего
  не шлёт, её ход идёт дальше.

### 5.3 Фреймы hub → worker
- `session.start` {session_id, mode, runtime, acp_agent?, model?, workspace_path | null,
  cwd, environment, runtime_session_id?, system_prompt?, disallowed_tools[], restricted,
  auto_approve, session_token, owner_is_worker_owner, ask_timeout_s, requested_by_owner?}
  — `mode`: `new` | `resume` (§5.2); `requested_by_owner` (передаётся только `true`) —
  workspace сессии добавил владелец воркера: подтверждение новой папки не нужно (§10.2); воркер вызывает `start` или `resume` адаптера (§8),
  адаптер Claude Code при `new` всё равно проверяет jsonl с этим uuid и при наличии
  продолжает его через `--resume` (§8.1); `owner_is_worker_owner` нужен воркеру для `allow_foreign_sessions`, выбора
  профиля Hermes и допуска `isolation: none`; `ask_timeout_s` — чтобы выставить
  таймаут MCP-инструмента рантайма (§7.1); без `model` воркер берёт модель рантайма
  по умолчанию. `workspace_path` — `path` из записи workspace сессии; воркер принимает
  его, только если путь, раскрытый со симлинками, — каталог внутри `allowed_roots`, и
  проверяет `cwd` против него (§8.1), иначе `error {invalid_frame}`.
- `session.input` {session_id, event_id, text, artifact_ids[],
  peer_prefix[{from: "<project-slug>/<session-slug>", text, ts}]} —
  артефакты воркер скачивает через `GET /worker/artifacts/{id}` своим токеном
  (без TTL) в `<workspace>/<cwd>/.hqc/inbox/<event_id>/` и подставляет пути; папка
  `.hqc/` добавляется в `.git/info/exclude` workspace. `peer_prefix` — накопленные
  `send`-сообщения (§7.1).
- `session.stop` {session_id} — прервать текущий ход.
- `session.steer` {session_id, text} — вмешаться в ход без прерывания, если рантайм
  умеет (Hermes: `/steer`, §8.2.1); иначе `error`.
- `session.kill` {session_id} — завершить процесс агента.
- `approval.response` {session_id, request_id, option_id},
  `clarify.response` {session_id, request_id, answers}; поля `by` во фреймах нет, оно
  только в событиях. Фрейма `approval.cancel` нет: отменяя запрос сам (таймаут, `stop`,
  архивация), хаб пишет событие `approval.cancel` и шлёт воркеру
  `approval.response` с `option_id` варианта `canonical: deny`, чтобы адаптер закрыл
  запрос в рантайме. Так же для `clarify`: хаб пишет событие `clarify.cancel` и шлёт
  `clarify.response` с `answers: {}` — пустой объект означает отмену; адаптер Claude
  Code отвечает на `can_use_tool` для `AskUserQuestion` поведением `deny`, модель
  продолжает ход без ответов.
- `fs.stat` {request_id, path} → `result {request_id, exists, is_dir, canonical?,
  inside_allowed_roots}` — проверка папки перед созданием workspace (§13.1). `canonical` —
  путь с раскрытыми симлинками, есть, если путь существует; `inside_allowed_roots` считается
  по нему (для несуществующего — по ближайшему существующему предку). Вне `allowed_roots`
  воркер о пути ничего не сообщает: `{exists: false, is_dir: false, inside_allowed_roots:
  false}`. Относительный путь — `error {invalid_frame}`.
- `fs.list_dirs` {request_id, path | null} → `result {request_id, entries[{name, path}]}`
  — дерево папок для выбора workspace в клиенте: при `path: null` — `allowed_roots`, иначе
  подкаталоги `path` (только каталоги, без скрытых, симлинки — только на каталоги внутри
  `allowed_roots`, сортировка по имени без учёта регистра, не больше 500). Путь вне
  `allowed_roots` (после раскрытия симлинков) — `error {invalid_frame}`.
  У обоих кадров `request_id` равен `id` кадра; ответ — `result` или `error` с тем же `id`.
  Хаб ждёт ответ 10 с (`504 worker_timeout` в REST, §6).
- `workspace.create` {request_id, kind: clone|worktree|dir, path, origin_url?,
  origin_path?, branch?, requested_by_owner} → `result {ok, path, error?}`
- `workspace.delete` {request_id, path, requested_by_owner} → `result` (§13.2)
- `workspace.list_candidates` {request_id} → `result {request_id, candidates[{path,
  sessions_count, last_active}]}` — папки с транскриптами Claude Code (§9.1): `path` — `cwd`
  записей, только внутри `allowed_roots`, сортировка по пути; `last_active` — время изменения
  самого свежего файла. `request_id` равен `id` кадра, ждёт хаб 10 с, как `fs.*`. Воркер без
  зеркала отвечает `error {invalid_frame}`.
- `mirror.set` {workspace_path, enabled} → `ack` — следить за транскриптами папки (§9.2) или
  перестать. Хаб шлёт после каждого `hello` для всех workspace воркера с `mirror_enabled`, при
  создании такого workspace и с `enabled: false` при его удалении. Воркер с `enabled: true`
  принимает только существующую папку внутри `allowed_roots` (после раскрытия симлинков),
  иначе `error {invalid_frame}`; список держит в памяти.
- `model.proxy` {request_id, model, body} → поток `model.proxy.chunk {request_id, data}`
  и `model.proxy.end {request_id, error?}`
- `worker.approval.response` {request_id, option_id} → `ack` — ответ владельца воркера на
  `worker.approval.request` или `deny` при отмене хабом (истечение); воркер отвечает `ack` и
  тогда, когда запроса у него уже нет. Не подтверждённый ответ хаб досылает после `hello`
  (без `session.start`, §10.2).
- `mcp.result` {request_id, result | error}

### 5.4 Фреймы worker → hub
- `hello` {protocol_version, boot_id, capabilities, environments[], env_bindings[],
  allowed_roots[], allow_foreign_sessions, share_local_models, local_models[]}
  — `boot_id`: uuid, новый на каждый запуск процесса воркера, одинаковый во всех `hello`
  этого процесса (§5.2, §17.3). `capabilities` — `{claude_code?: {version,
  sessions_registry?}, acp_agents[]}`; `sessions_registry: true` — воркер читает реестр живых
  сессий Claude Code и сообщает держателей (§9.3).
  Workspace воркер не сообщает (с 0.16; поле итерации 1 `capabilities.workspace_path` хаб
  больше не читает): workspace создаются в хабе (§3, §6) и проверяются воркером по
  `allowed_roots`.
- `event` {event} → `ack` (`session_id` внутри события)
- `session.state` {session_id, process_state, runtime_session_id?, locked_by, title?, held_by?}
  — `title`: заголовок, который дал сессии рантайм (§8.1); воркер повторяет последний во
  всех следующих `session.state`, хаб применяет его по правилу `title_source` (§3 Session),
  приводя к одной строке до 200 символов. `held_by` — держатель транскрипта (§9.3): поля нет —
  у воркера нет данных реестра, `null` — никто, `{entrypoint, status}` — живой чужой процесс.
  **Отчёт о держателе** — `session.state` с nil `session_id`, `runtime_session_id` транскрипта и
  `held_by` (`process_state: stopped`, `locked_by: none` — хаб их не читает): хаб ищет сессию
  по воркеру и `runtime_session_id` (нет такой — только `ack`) и применяет `held_by` по §9.3.
  Отчёты идут через outbox в одном порядке с `mirror.event`, ответ — `ack {}`.
- `mirror.event` {workspace_path, runtime_session_id, cwd, event, title?, recent, held_by?} — события из
  зеркала (§9.1, §9.2), через outbox, ответ — `ack {event_id, seq}` как на `event` (дубль —
  `seq` сохранённого, папка не под зеркалом этого воркера или `cwd` вне неё — без `seq`).
  `workspace_path` — путь из `mirror.set`, `cwd` — абсолютный путь из записи, `title` —
  последний `ai-title` файла, `recent` — файл изменён меньше 30 с назад, когда воркер читал
  запись, `held_by` — держатель транскрипта в момент чтения, как в `session.state`. Хаб ищет
  сессию по воркеру и `runtime_session_id` и создаёт её для неизвестного; `event.session_id`
  (воркер ставит nil uuid) и `author.id` игнорирует и заполняет сам (у `system` — `{kind:
  system}`).
- `worker.approval.request` {request_id, kind, description, expires_at} → `ack {}` —
  подтверждение владельца вне сессии (`kind`: `workspace.use`, позже `workspace.create`,
  `workspace.delete`; список открытый). Хаб пишет `approval.request` в служебную сессию
  воркера; повтор с тем же `request_id` после переподключения нового события не пишет (§10.2).
- `mcp.call` {request_id, session_token, tool, args}
- `mcp.cancel` {request_id, reason} — отмена отложенного вызова (§5.2, §7.2)
- `result` {request_id, ...} / `error` на запросы хаба (`fs.stat`, `fs.list_dirs`,
  `workspace.list_candidates`, §5.3), с `id` запроса.
- Загрузка артефактов: HTTP PUT `/worker/artifacts` с токеном воркера, не по WebSocket.
  Лимит артефакта **100 МБ**, нарезки на части нет.

## 6. Протокол Client ↔ Hub

Авторизация: хаб проверяет подпись JWT `Cf-Access-Jwt-Assertion` по JWKS Cloudflare
(issuer и audience из конфига) и берёт email из токена. Заголовок с email без JWT
не принимается. Маршрут воркеров `/worker/*` исключён из Access и принимает только
токены воркеров; маршрут людей `/api/*` принимает только JWT Access. Хаб слушает только
интерфейс туннеля.

Dev-режим (локальная разработка без Access): `HQC_DEV=1` вместе с `HQC_DEV_USER=<email>`,
все запросы `/api/*` идут от этого пользователя. Хаб отказывается стартовать, если
при этом заданы `HQC_ACCESS_*` или `HQC_HUB_LISTEN` — не loopback (`127.0.0.0/8`,
`[::1]`, `localhost`); при старте пишет громкое предупреждение (§20).

Тела REST и фреймы `/api/ws` типизированы в `hqc-proto` (`api`, `client_frame`),
примеры-контракт — `examples/wire/api.*.json` и `client.*.json`; их читают тесты хаба
и клиента. Неизвестные поля игнорируются в обе стороны.

- `POST /api/push/subscribe` (тело — `PushSubscription.toJSON()`: `{endpoint,
  expirationTime?, keys: {p256dh, auth}}`), `DELETE /api/push/subscribe {endpoint}`,
  `GET /api/push/vapid` → `{public_key}` (base64url несжатой точки P-256; `null`, если
  push не настроен — клиент показывает «уведомления на хабе выключены»). Тело самого
  push — §16. `endpoint` — только `https://` на хостах push-сервисов (§20), иначе `400`;
  не больше 10 подписок на пользователя (`409 push_limit`); чужой `endpoint` — `409
  conflict`, а не перехват; свою подписку повторный запрос обновляет.
- позже: `/api/schedules` (ScheduledMessage), `/api/projects/{id}/template`

Объект сессии (`GET /api/sessions/{id}`, список, создание, `PATCH`, `archive`):
`{id, project_id, owner_id, workspace_id?, worker_id?, cwd, title, title_source, slug, agent: {runtime,
acp_agent?, model?, runtime_session_id?, process_state, system_prompt?,
disallowed_tools[], restricted, start_failures}, auto_approve, wake_on_send, locked_by,
last_seq, archived, system?, held_by?, state, queue_len, last_read_seq, unread, created_at,
updated_at}`. `held_by` (`{entrypoint, status}`) — сессию сейчас держит открытой Claude Code вне
hqc (§9.3): `state: locked_vscode`, подхват — `409 vscode_open`, пока её не закроют там.
`system: true` — служебная сессия воркера (§10.2): ввод, `stop`, `retry`, `takeover`,
`archive` и `DELETE` — `409 system_session`, `PATCH auto_approve: true` — `403`.
`state`, `queue_len` (§17.1), `last_read_seq` и `unread` вычисляются для запросившего
пользователя.

WebSocket `/api/ws` (апгрейд только с `Origin` хаба, §20; сообщения до 1 МиБ): клиент шлёт `subscribe {session_id, after_seq}` и получает
события с `seq > after_seq`, затем живой поток; `agent.delta` без `seq`. Событие,
сохранённое из ввода клиента, несёт его `client_op_id`, чтобы клиент показывал
сообщение сразу и сверял с эхом (приём из Agent Host Protocol, §22). Отдельная
подписка `subscribe_summary` даёт `state`, `queue_len` и непрочитанное по сессиям.
После переподключения клиент повторяет `subscribe` с последним виденным `seq`.

Фреймы `/api/ws` — плоские JSON-объекты `{type, ...}` без `id` и без обёртки `payload`:
- клиент → хаб: `{type: subscribe, session_id, after_seq?}`, `{type: unsubscribe,
  session_id}`, `{type: subscribe_summary}`, `{type: ping}`;
- хаб → клиент: `{type: event, event}` — событие как хранится (§3), у `agent.delta` без
  `seq`; `{type: subscribed, session_id, last_seq}` — история после `after_seq` отдана,
  дальше живой поток; `{type: delivery, session_id, event_id, seq, delivery,
  delivered_at?}` — изменилась доставка ввода, само событие повторно не присылается,
  клиент обновляет у себя `delivery`/`delivered_at` события с этим `seq`;
  `{type: summary, sessions[]}` — ответ на `subscribe_summary`, все сессии пользователя;
  `{type: session.summary, session}` — изменилась одна сессия; элемент — `{session_id,
  project_id, title, state, queue_len, unread, last_seq, last_read_seq, held_by?}` (то же, что
  в объекте сессии); `{type: pong}`; `{type: error, code, message, session_id?}`.
  Неизвестный `type` клиент игнорирует.
- `unread` — число событий с `seq > last_read_seq` среди: `agent.message` с
  `final: true`, `approval.request`, `clarify.request`, `peer.message`, `system`, кроме
  `system` с кодом `worker_log` (логи воркера в служебной сессии, §10.2). Промежуточные
  `agent.message` (`final: false`), `status`, `usage`, вызовы инструментов и вводы
  непрочитанным не считаются.

Сессия создаётся в workspace своего проекта (§13.4) и на его воркере: `workspace_id` —
этот workspace (другого проекта, или не на `worker_id`, если тот задан, — `400`); без
`workspace_id`, но с `worker_id` — workspace проекта на этом воркере (default, если он там,
иначе самый ранний); без обоих — `default_workspace_id` проекта. Нет такого — `409
no_workspace`. Так только что зарегистрированный (возможно, по присланной ссылке, §5.1)
воркер не получает новые сессии, пока пользователь сам не добавит на нём workspace и не
выберет его. Правило «воркер по умолчанию» итерации 1 и код `409 no_worker` сняты.

Ограничения полей: `title` — до 200 символов; `model` — `^[A-Za-z0-9._:-]{1,64}$` и не с
`-` (уходит в командную строку агента); `client_op_id` — до 128 байт; иначе `400`.

Ошибки REST: `{error: <code>, message}` с HTTP-статусом (у `workspace_conflict` — с
дополнительными полями, у `locked_vscode` — `hint` и `held_by?`, у `vscode_open` — `held_by`);

тишины без данных реестра, §9.3), `system_session` (служебная сессия
воркера, §10.2), `request_closed`, `no_workspace`, `worker_offline`, `workspace_conflict`,

второго — `sessions_count`); `400` — `bad_request`,
`unknown_artifact` (§12) и коды проверки пути (`outside_allowed_roots`, `path_not_found`,
`not_a_directory`, `invalid_path`); `504
worker_timeout` — воркер не ответил на запрос хаба; `403` — чужой `Origin` (§20); `429` и

отдаётся общим текстом, причина — в лог хаба. `GET .../events`

## 7. MCP-инструменты для агентов

Воркер поднимает MCP-сервер hqc и подключает его к рантайму каждой сессии.
Идентификация: MCP-сервер — stdio-процесс, который рантайм запускает сам (через
`--mcp-config` у Claude Code, JSON передаётся строкой, без файла; через поле
`mcpServers` в `session/new` у ACP-агентов); воркер передаёт ему `session_token`
из `session.start` через переменную окружения, а MCP-процесс ходит в демон воркера
по локальному сокету с этим токеном; демон пересылает вызов в хаб фреймом `mcp.call`
(§5.2). Токен выдаёт хаб, он не попадает к агенту в контекст и в транскрипт: Hermes
хранит `mcpServers` из `session/new` только в памяти работающего агента, в базу
сессий не пишет (проверено по исходникам). Ограничение: другой процесс того же
пользователя ОС может прочитать окружение процесса; это та же мягкая граница, что
в §14. Голая модель на хабе получает те же инструменты напрямую. Инструменты hqc
вызываются без подтверждения: Claude Code запускается с `--allowedTools mcp__hqc` (§8.1).

Инструменты действуют с правами владельца сессии; у агента своих прав нет.

- `hqc_attach(path?, content?, name?, kind?, caption?)` — загрузить файл как артефакт
  в текущую сессию; `path` для рантаймов с файловой системой, `content` для голой модели.
- `hqc_send(text, session?)` — сообщение в другую сессию без ожидания ответа; без
  `session` — в персональную сессию-ассистент владельца.
- `hqc_ask(text, session, timeout_s?)` — сообщение с ожиданием ответа. В свою же
  сессию — ошибка сразу.
- `hqc_spawn(project, workspace, runtime?, model?, prompt)` — создать сессию и агента,
  вернуть адрес. `workspace` обязателен, если у проекта нет `default_workspace_id`.
- `hqc_list_sessions(project?)` — адреса, названия, статусы.
- `hqc_search_history(query, project?, fuzzy?)` — поиск по истории с учётом грантов.
- `hqc_schedule(session, at|cron, message)` — крон хаба (§16).

Адрес сессии: `<project-slug>/<session-slug>` или id. Slug уникален в проекте и не
меняется при переименовании.

### 7.1 Семантика send и ask **[решение]**

Доставка:
- `peer.message` всегда доставляется агенту как **текст ввода** с заголовком
  `[hqc peer from <project>/<session> | mode=ask | request_id=... | reply with your final message]`
  или `... | mode=send]`. Так агент отличает ask от send в любом рантайме.
- Защита от подделки: при сборке `session.input` воркер экранирует подстроку
  `[hqc peer` (в любом месте текста, регистронезависимо) в `[hqc-peer-text`
  во **всём** тексте, который кладёт в рантайм, — в тексте пользователя, в тексте
  peer-сообщения от агента и в блоке `peer_prefix`; настоящий заголовок добавляется
  после экранирования. История в хабе не переписывается.
- Права: `hqc_send`/`hqc_ask` в чужую сессию требуют у владельца сессии-отправителя
  гранта `write` на целевую.

Очереди (две разные):
- **Очередь ввода** сессии (§17.2): `user.message` и `peer.message` с `mode=ask`.
  Каждый элемент запускает отдельный ход, строго по `seq`.
- **Буфер send**: `peer.message` с `mode=send` при `wake_on_send: false` хода не
  запускает; хаб копит такие сообщения и передаёт их в `peer_prefix` следующего
  `session.input`; воркер подклеивает их перед текстом ввода блоком «Сообщения от
  других сессий». Буфер очищается по `ack` на ввод, который его нёс. Лимит буфера —
  50 сообщений или 64 КБ; старшие вытесняются с событием `system`. При
  `wake_on_send: true` send идёт в очередь ввода как ask без ожидания ответа.

Ответ на ask:
- Ответом считается `agent.message` с `final: true` и `in_reply_to`, равным `event_id`
  этого `peer.message`. Возвращается как `mcp.result` блокирующему вызову.
- Целевая сессия `locked_vscode` — немедленная ошибка. `worker_offline` — ожидание
  до таймаута. Таймаут по умолчанию 10 минут (`ask_timeout_s` в `session.start`).
- Таймаут инструмента в рантайме воркер выставляет не меньше `ask_timeout_s` плюс
  минута: Claude Code — `MCP_TOOL_TIMEOUT` в env процесса, в миллисекундах; по умолчанию
  он практически не ограничен (1e8 мс), поэтому воркер всегда выставляет его явно как
  `(ask_timeout_s + 60) * 1000` (проверено на 2.1.307). Отдельно у stdio MCP-серверов Claude Code действует idle-таймаут
  30 минут (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`): вызов без ответа и без progress-уведомлений
  обрывается через 1800 с даже при большом `MCP_TOOL_TIMEOUT`, поэтому MCP-сервер hqc
  во время ожидания `hqc_ask` шлёт progress (§7.2; проверено на 2.1.307); Hermes — `mcp.tool_call`
  в конфиге профиля (по умолчанию 300 с, проверено по исходникам); другие
  ACP-агенты — по их документации **[проверить]**.
- Открытые `ask` хранятся в `PendingRequest`; после перезапуска воркера-отправителя
  блокирующий вызов потерян, `ask` закрывается с ошибкой (§5.2).

Цепочки:
- `chain_id` создаётся при первом `ask`/`send` из хода, начатого человеком; `depth`
  растёт на каждом `ask` (лимит 3), `hops` — на каждом `peer.message` в цепочке
  (лимит 20). Хаб хранит `chain` ввода, начавшего текущий ход, и отдаёт его
  MCP-серверу в ответе на первый `mcp.call` сессии, чтобы тот ставил его на исходящие.
- При превышении лимита инструмент возвращает ошибку; продолжить цепочку может только
  ход человека. Взаимная блокировка (A ждёт B, B ждёт A) разрешается таймаутом.

### 7.2 Требования к MCP-серверу hqc
- Stdio-процесс `hqc-worker mcp`, который запускает сам рантайм: Claude Code — через
  `--mcp-config` строкой JSON, ACP-агенты — через `mcpServers` в `session/new` (§7).
- `session_token` получает только из переменной окружения; не пишет его в ответы
  инструментов, логи рантайма и файлы (§7).
- Каждый вызов пересылает демону воркера по локальному сокету с этим токеном; демон
  отправляет его в хаб фреймом `mcp.call` (§5.2). Своего состояния, кроме `chain` текущего
  хода (§7.1), не держит.
- Имя сервера в конфиге рантайма — `hqc`, инструменты — `hqc_*`; у Claude Code они
  разрешены заранее через `--allowedTools mcp__hqc` (§8.1).
- Пока вызов ждёт ответа (`hqc_ask`), шлёт `notifications/progress` с `progressToken` из
  `params._meta` вызова не реже раза в минуту. Без этого Claude Code обрывает вызов через
  30 минут простоя (§7.1); серверу при этом `notifications/cancelled` не приходит.
- Если рантайм отменил вызов (`notifications/cancelled`, например по `MCP_TOOL_TIMEOUT`)
  или MCP-процесс завершился с открытым вызовом (EOF на stdio), демон воркера закрывает
  соответствующий `PendingRequest` ask фреймом `mcp.cancel {request_id, reason}` (§5.4);
  обрыв по простою без уведомления предотвращается progress-уведомлениями, так что
  отдельной детекции для него нет.

## 8. Адаптеры рантаймов

Два адаптера на воркере: нативный для Claude Code (§8.1) и общий ACP (§8.2) для Hermes
и любого агента из ACP-реестра. Третий, голая модель, живёт в хабе (§8.3). Все
реализуют один интерфейс: `start`, `input`, `stop`, `steer?`, `kill`, `resume`,
`answer_approval`, `answer_clarify` плюс поток событий §4. Очередь ввода —
ответственность воркера, не адаптера (§17.2).

### 8.1 Claude Code
Процесс `claude -p --output-format stream-json --input-format stream-json
--include-partial-messages --replay-user-messages --permission-prompts host
--permission-prompt-tool stdio --strict-mcp-config --mcp-config '<json>'
--allowedTools mcp__hqc [--disallowedTools <правила…>] [--settings '<json [permissions]>']
(--setting-sources user,local | --restricted) --permission-mode <режим "спрашивать" | auto>
[--append-system-prompt <текст>] --session-id <uuid>` для новой сессии
(uuid назначает хаб, кладёт в `runtime_session_id`) и `--resume <uuid>` для
продолжения. Выбор между ними делает наличие транскрипта
`<config>/projects/<encoded cwd>/<uuid>.jsonl` (§9), а не `mode` из `session.start`:
и `start`, и `resume` адаптера при существующем файле используют `--resume`, иначе
`--session-id`. `--permission-prompt-tool stdio` обязателен: без него CLI ничего
не спрашивает у хоста, а сразу отклоняет всё, что требует подтверждения
(`system/permission_denied`, `permission_decision.source: config`), и `AskUserQuestion`
не попадает в список инструментов (проверено на 2.1.307). `--allowedTools mcp__hqc`
разрешает все инструменты MCP-сервера hqc, чтобы их вызовы не шли через `can_use_tool`
(§7); на 2.1.307 одинаково работают формы `mcp__hqc` и `mcp__hqc__*`, без флага
вызов MCP-инструмента приходит как `can_use_tool`. Проверено на 2.1.300: `--resume` продолжает тот же uuid и дописывает тот
же файл jsonl. `--strict-mcp-config` отключает MCP-серверы из `~/.claude.json`
и `.mcp.json` проекта; разрешить их можно только через окружение (§14,
`allow_local_mcp`). В env процесса — `MCP_TOOL_TIMEOUT` (§7.1): миллисекунды, по умолчанию
1e8 мс, минимум 1000 мс (проверено на 2.1.307).

Ограничения сессии не теряются молча **[решение]**: `disallowed_tools` → `--disallowedTools`
(каждое правило отдельным аргументом), `system_prompt` → `--append-system-prompt`,
`restricted` → `--restricted` (§8.4). Воркер отклоняет `session.start` (`invalid_frame`),
если `model` не `^[A-Za-z0-9._:-]{1,64}$` или начинается с `-`, или правило
`disallowed_tools` пустое, начинается с `-` или содержит управляющие символы.
Настройки чужого репозитория: в `-p` диалога доверия к папке нет, поэтому
`.claude/settings.json` из workspace (hooks, `defaultMode: bypassPermissions`) применился бы
без вопроса. Адаптер передаёт `--setting-sources user,local` (проектный файл не читается,
`settings.local.json` — читается: туда пишет `always`) и явный `--permission-mode` с
режимом «спрашивать»: в справке CLI 2.1.308 это `manual` (`default` в списке вариантов нет),
до этого — `default`; воркер при старте читает `claude --help` и выбирает имеющийся
(`[permissions] mode = "auto"` заменяет его на `auto`, §14). Проверено на 2.1.308 (T12,
фикстура `always-git-push`): с `--setting-sources user,local --permission-mode manual`
`always` по-прежнему предлагается и пишет правило в `settings.local.json`; `manual` в
`system/init` отображается как `"permissionMode": "default"`.
Окружение процесса очищается: из окружения воркера проходят только `PATH`, `HOME`, `USER`,
`LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TERM`, `TMPDIR`, `SSH_AUTH_SOCK`, `CLAUDE_*`,
`ANTHROPIC_*`, затем переменные окружения workspace (§14); `HQC_*` — никогда. Рабочий
каталог воркер хранит каноническим, требует его существования и перепроверяет перед
каждым запуском процесса (символическая ссылка могла смениться). Не больше `max_sessions`
(локальный конфиг, по умолчанию 8) процессов агентов одновременно; следующий старт —
`error {agent_start_failed, retryable: true}`.

Идентификаторы. Проверено на 2.1.307: `uuid` у сообщений `assistant` и `user`
(включая `tool_result`) в stream-json **совпадает** с `uuid` соответствующих записей
в jsonl. Поэтому адаптер выводит `event_id` как uuid v5 от этого `uuid`, как и зеркало
(§3 Event, §9.2). Запись исходного промпта пользователя в stream-json без эха
не приходит: её `uuid` адаптер берёт из эха `--replay-user-messages` (`isReplay: true`);
проверено на 2.1.307: `uuid` эха равен `uuid` записи промпта в jsonl.

Вложения ввода (`session.input.artifact_ids`, §5.3, §12). До передачи ввода рантайму
воркер скачивает каждый артефакт `GET /worker/artifacts/{id}` своим токеном (без
редиректов) в `<workspace>/<cwd>/.hqc/inbox/<event_id>/<имя>`. Имя — из заголовка
`x-hqc-artifact-name` ответа (percent-encoded UTF-8), санируется воркером: последний
компонент пути, управляющие и `:*?"<>|` → `_`, без ведущих точек и пробелов и без
завершающих, до 120 байт с сохранением расширения, пустое — `file`; совпадающие в одном
вводе (без учёта регистра) получают `-2`, `-3`… перед расширением. Каталоги `.hqc`,
`inbox`, `<event_id>` создаются по одному внутри канонического рабочего каталога, ни один
не может быть символической ссылкой; файл пишется во временный и переименовывается на
место. Если workspace — git-репозиторий (каталог `.git` или файл `.git` worktree, тогда
общий git-каталог из `commondir`), в его `info/exclude` добавляется строка `.hqc/`. К
тексту ввода добавляется блок: пустая строка, `Вложения:` и по строке `- <путь>` на файл,
пути относительно рабочего каталога (`.hqc/inbox/<event_id>/<имя>`); пустой текст — только
блок. Картинки (`kind: image`, `image/png|jpeg|gif|webp`, до 5 МБ) дополнительно идут в
user message stream-json: `content` — массив из текстового блока и блоков `{type: image,
source: {type: base64, media_type, data}}` (формат Messages API; **[проверить]** на живом
CLI, фикстура `crates/hqc-worker/fixtures/inbox`). Артефакт, который хаб не отдаёт (`401`,
`403`, `404`, `410`), — ввод отклоняется `error {internal, retryable: false}` (у хаба —
`input_rejected`); сеть и диск — `retryable: true`; частично скачанное удаляется.

Разрешения: при `--permission-prompts host --permission-prompt-tool stdio` запрос приходит в stdout как
`control_request` с `subtype: can_use_tool` (`tool_name`, `input`,
`permission_suggestions`); адаптер отвечает `control_response` с `behavior:
allow|deny`. Варианты для клиента: `once`, `session`, `always`, `deny`
(`always` только если среди `permission_suggestions` есть `addRules` в `localSettings`). Маппинг: `once` → allow;
`deny` → deny; `always` → allow плюс `updatedPermissions`, Claude Code сам пишет
правило в `.claude/settings.local.json` **корня git-репозитория, содержащего cwd**
(или самого cwd, если репозитория нет; проверено на 2.1.308). Правило адаптера: в
`updatedPermissions` идут только элементы `permission_suggestions` с `type: addRules`
и `destination: localSettings`, остальные подсказки (`setMode`, `addDirectories`
и т.п.) отбрасываются — иначе сессия переключается в `acceptEdits` и расширяет
список каталогов (проверено на 2.1.307). Если таких элементов нет, `always`
не предлагается; `session` → allow и правило в адаптере
до конца процесса; для `Bash` и других инструментов, выполняющих команды, подсказка без
`ruleContent` («весь инструмент») в правило сессии не превращается — запоминается только
точный ввод. В `--restricted` (§8.4) локальные настройки не применяются,
`always` маппится в `session`. Хаб постоянные разрешения не хранит. Инструмент
`AskUserQuestion` приходит тем же `can_use_tool`: адаптер превращает его
в `clarify.request`, присваивая вопросам свои `id`, ответы возвращает через
`updatedInput.answers`, ключи которых — текст вопроса, а значения — `label` варианта
(адаптер сам сопоставляет `id` с текстом). Формат
`control_request`/`control_response` проверен на 2.1.307 при `--permission-prompt-tool stdio`
: точные JSON — `docs/notes/claude-control-protocol.md`, фикстуры —
`crates/hqc-claude-jsonl/fixtures/*-2.1.307.jsonl`.

Маппинг stream-json на §4: `stream_event` text delta → `agent.delta`; `assistant`
с текстом → `agent.message`, причём адаптер придерживает последний текст до
следующего элемента потока: `tool_use` → `final: false`, `result` → `final: true`;
`tool_use` → `tool.call`; `tool_result` → `tool.result`; `result` → `usage` и
`status idle`; эхо `--replay-user-messages` — сообщение `user` с `isReplay: true` —
→ `ack` на `session.input` (по этому полю эхо отличается от `user` с `tool_result`).
CLI повторяет в stdout каждый `control_response`, который адаптер отправил в stdin;
адаптер такие строки пропускает. `in_reply_to` = `event_id` ввода, который адаптер
отправил последним.

Не каждый вызов инструмента спрашивает разрешение: команды только для чтения (например,
`echo`) CLI разрешает сам, без `can_use_tool`, поэтому `approval.request` приходит не на
каждый `Bash` (проверено на 2.1.308 живым прогоном T4).

Политика разрешений воркера (`[permissions]`, §14). Списки `allow` и `deny` уходят в CLI
при каждом запуске процесса как `--settings '{"permissions":{"allow":[…],"deny":[…]}}'`,
в том числе с `--restricted` (CLI применяет `--settings` и там). Проверено на 2.1.308
(T12, `docs/notes/claude-control-protocol.md`, «Permission policy, 2.1.308»):

- вызов под `allow` выполняется без `can_use_tool`; вне обоих списков — спрашивается, как
  обычно;
- вызов под `deny` не выполняется и **не спрашивается**: `can_use_tool` нет, в stream-json
  приходят `system` `permission_denied` (`tool_name`, `tool_use_id`, `message`,
  `decision_reason_type` `rule`/`subcommandResults`), `tool_result` с `is_error: true` и
  запись в `result.permission_denials`. Адаптер превращает `permission_denied` в событие
  `system` с кодом `policy_denied` (§4), `tool.result` с ошибкой приходит как обычно;
- deny из `--settings` сильнее allow, которое `always` записал в `settings.local.json`, и
  сильнее режима `auto`; это гарантирует CLI;
- инструмент, запрещённый целиком (`WebFetch`), пропадает из списка инструментов сессии;
- правила Bash: `Bash(x:*)` — префикс до границы слова, `*` внутри — любая
  последовательность символов (`Bash(curl * | sh)`), команда с `&&`, `;`, `|` сверяется по
  каждой подкоманде.

Адаптер читает те же правила сам (вторая линия): `can_use_tool`, подходящий под `deny`,
он отклоняет без карточки (на него не может ответить ни `always`, ни `auto_approve` хаба) и
пишет `system policy_denied`; в остальных `approval.request` кладёт `policy_hint`: `allow`,
если вызов подходит под правило `allow` целиком (CLI всё же спросил), иначе поля нет.
Адаптер понимает имя инструмента, сервер MCP (`mcp__hqc`) и правила `Bash` (префикс, `*`,
точная команда); прочие (`Read(./x/**)`, `WebFetch(domain:…)`) оставляет CLI.

Режим `auto` (`--permission-mode auto`, проверено на 2.1.308): CLI решает сам и **никогда
не спрашивает** — классификатор пропустил и `rm -rf` вне workspace, и `git push --force`,
и `sudo`, если об этом просил пользователь; признак решения есть только в
`tool_result_meta[].permission_decision.reason_type` (`classifier`, `mode`). Единственная
граница в этом режиме — `deny`.

Прерывание хода (`session.stop`): адаптер шлёт в stdin `control_request {subtype:
"interrupt"}`; CLI завершает ход записью `result` с `subtype: error_during_execution`,
частичный текст ответа приходит отдельной записью `assistant`, процесс остаётся жив
(проверено на 2.1.308). Если `result` нет за 10 с, группе процесса уходит SIGINT; CLI
на нём завершается, и следующий ввод поднимает процесс через `--resume`.

Рабочий каталог — `<workspace>/<cwd>`. Окружение процесса — из привязки пути
workspace в локальном конфиге воркера (§14). Авторизация — подписка, уже залогиненная
на машине (Keychain на маке); хаб её не хранит и не видит.

Заголовок сессии. Claude Code пишет в транскрипт запись
`{"type": "ai-title", "aiTitle": "<заголовок>", "sessionId": "<uuid>"}` — заголовок,
который модель придумала по первому промпту, иногда несколько раз за сессию (действует
последняя; фикстура `tool-call-2.1.307`, записи идут сразу после первого промпта, до
ответа модели). Адаптер после каждого завершённого хода читает транскрипт и, если
последний непустой `aiTitle` отличается от уже отправленного, шлёт хабу `session.state`
с полем `title` (§5.4); хаб применяет его по правилу `title_source` (§3 Session).
Проверено на 2.1.308 (T13, живой прогон `live_ai_title`): с `--input-format stream-json`
CLI `ai-title` **не пишет** ни к концу хода, ни через 5 с после него; во всех
транскриптах T0 (2.1.307) и T12 (2.1.308), снятых в этом режиме, его тоже нет — он есть
только в прогоне с промптом аргументом (`tool-call-2.1.307`). Поэтому в итерации 1
сессии адаптера на практике остаются с заголовком по умолчанию, пока CLI не начнёт писать
`ai-title` в этом режиме или его не переименует пользователь **[проверить]** на
следующих версиях CLI.

Встроенные инструменты Claude Code `ListAgents` и `SendMessage` находят другие сессии
Claude на той же машине и вбрасывают им сообщения напрямую, минуя хаб: вторая сессия
получает ход без входного события в истории. Воркер всегда добавляет их в
`--disallowedTools`; `allow_native_messaging = true` в `worker.toml` возвращает их.
Общение агентов идёт через `hqc_send`/`hqc_ask` (§7).

### 8.2 ACP-агенты (общий адаптер)
Адаптер запускает **отдельный ACP-процесс на каждую сессию hqc** (stdio JSON-RPC)
с окружением workspace (§14). Команда запуска — из локального конфига воркера по
имени `acp_agent`, абсолютным путём (в неинтерактивной оболочке `hermes` не в PATH).
При старте воркер делает `initialize` каждому сконфигурированному агенту и кладёт
в `hello.capabilities.acp_agents` его `load_session`, `resume`, `image`, `isolation`
и версию; отсутствие бинарника видно до создания сессии.

Инициализация: адаптер объявляет `clientCapabilities.fs` и `terminal` **недоступными** —
воркер не реализует чтение/запись файлов и терминал по просьбе агента. Если
`initialize` требует `authenticate` (провайдер не настроен), адаптер пишет `system`
«агент не настроен на воркере» и завершает старт ошибкой (§5.2).

Маппинг на §4: `session/new {cwd, mcpServers}` → создание; `session/prompt` → ход,
`ack` на `session.input` сразу после отправки; `session/update` с
`agent_message_chunk` → `agent.delta`/`agent.message`, `agent_thought_chunk` →
`agent.thinking`, `tool_call`/`tool_call_update` → `tool.call`/`tool.result`.
Конец хода — ответ на `session/prompt` со `stopReason`: адаптер придерживает
последний текст, при `tool_call` ставит `final: false`, при ответе на `session/prompt` —
`final: true`; `stopReason: cancelled` → без финального сообщения, `status idle`.
Диффы из `tool_call` сохраняются артефактом `kind: diff` и ссылаются из
`tool.result.artifact_id`, в `result_preview` — первые 4 КБ. `session/request_permission`
→ `approval.request` с **реальными** `options[]` агента (по `optionId`), `canonical`
по `kind` и имени; ответ — выбранный `optionId`. `session/cancel` → `session.stop`.
Resume — `session/load`, если агент объявил `loadSession`; иначе `session/new`
и пересказ истории адаптером. Адаптер **сверяет `sessionId` в ответе
`session/load`/`session/resume` с запрошенным** и при расхождении останавливается
с ошибкой: агент мог молча создать новую сессию. `usage` — только если агент отдаёт
токены; `clarify` в ACP нет. Повторный `session/prompt` во время хода адаптер
не отправляет никогда: очередь ввода ведёт воркер (§17.2), даже если агент умеет
ставить промпты в собственную очередь — иначе расходится `in_reply_to`.

Сессии без workspace для ACP-агентов не допускаются (§8.4): у них нет аналога
`--restricted`.

Claude Code через ACP (`@agentclientprotocol/claude-agent-acp`, Node, поверх Agent
SDK) **не используется**: нативный адаптер §8.1 проверен, даёт `--restricted`,
`--strict-mcp-config`, `--session-id` и control-протокол напрямую, без Node
на воркере.

#### 8.2.1 Особенности Hermes
Проверено по исходникам на llm-server, версия canary
`v0.21.4+canary.20261005T071900Z-434-g4787e4d56f` (коммит `4787e4d5`); у canary нет
стабильного номера, фиксируется хэш.

- Запуск: `~/.local/bin/hermes-acp` (или `hermes acp`) с профилем через `HERMES_HOME`.
  Профиль задаётся **локальной привязкой** в `env_bindings`, не хабом (§14).
  Это не messaging-гейтвей (`hermes-gateway.service`), тот не трогается.
- `initialize` объявляет `load_session`, `image`, `fork`, `list`, `resume`
  (методы ACP v2 включены через `use_unstable_protocol`).
- Воркер **всегда** ставит `HERMES_ACP_SKIP_CONFIGURED_MCP=1`, если окружение
  не разрешает `allow_local_mcp`. MCP hqc передаётся в `session/new` полем
  `mcpServers`; Hermes регистрирует их на сессию, переподключает при
  `session/resume` и не персистит.
- Варианты разрешений строятся динамически: `allow_once` всегда; `allow_session`
  и `deny_always`, если не `once_only`; `allow_always` только при `allow_permanent`;
  правки файлов идут отдельным запросом только с `allow_once`/`deny`. Маппинг
  по `option_id`: `allow_once` → once, `allow_session` → session, `allow_always` →
  always, `deny` / `deny_always` → deny. `allow_session` имеет `kind: allow_always`,
  поэтому по `kind` маппить нельзя.
- Таймаут `approvals.timeout` (300 с, читается на каждый запрос) →
  `approval.cancel {timeout}`.
- `session/resume` с неизвестным id **молча создаёт новую сессию** с warning в логе
  **[проверить]** — поэтому сверка id из §8.2 обязательна.
- `usage_update` в ACP у Hermes — оценка занятости контекста, не токены хода:
  в `usage` не переводится.
- Steer: текст промпта `/steer <text>` вмешивается в активный ход, `/queue <text>`
  ставит в очередь Hermes. Адаптер реализует `session.steer` через `/steer`;
  `/queue` не используется (очередь ведёт воркер).
- Toolset `hermes-acp` — без messaging, cron и `clarify` (проверено в `toolsets.py`).
  Память Hindsight и скиллы профиля работают как обычно, поэтому в чужих сессиях
  используется отдельный профиль (§11.1, §14).
- Сессия Hermes однописательная: сессию, которую ведёт Telegram-гейтвей, hqc не
  ведёт параллельно; её транскрипт можно только продолжить новой сессией hqc.
- На гейтвее дополнительно включается `api_server` (нужен `hermes peer` и Jobs API);
  адаптер им не пользуется.
- Каждая сессия — отдельный Python-процесс; рекомендуемый `idle_timeout` 30 минут.

### 8.3 Голая модель
Исполняется в хабе: OpenRouter, Anthropic API или локальная модель через прокси
воркера (§8.5). Цикл: модель ↔ MCP-инструменты hqc (§7), файловой системы нет.
Рантайм персональной сессии-ассистента по умолчанию, если при её создании нет
онлайн-воркера с Claude Code; позже меняется в настройках сессии.

### 8.4 Сессия без workspace
Для архитектурных обсуждений. Варианты: голая модель (§8.3) или Claude Code
на воркере `worker_id` во временной пустой папке `<worker-data>/scratch/<session_id>`
(`$HQC_HOME/scratch/<session_id>`, 0700; `session.start` с `workspace_path: null` и
`restricted: true`, без `restricted` — `invalid_frame`) с флагом `--restricted` (убирает инструменты, запускающие команды, и ограничивает
файловые инструменты рабочим каталогом). Работает на подписке. Воркер выбирает
пользователь при создании; по умолчанию — последний использованный онлайн-воркер
с Claude Code. ACP-агенты здесь не допускаются.

### 8.5 Локальные модели
Воркер объявляет в `hello` локальные OpenAI-совместимые endpoint'ы (на llm-server это
`ninfer` на 127.0.0.1:8082, модель qwen3.8-27b). Хаб проксирует запросы голой модели
фреймами `model.proxy` со стримингом чанков. По умолчанию локальные модели доступны
только сессиям владельца воркера; `share_local_models: true` в локальном конфиге
открывает их голым моделям коллег в расшаренных проектах.

## 9. Зеркало и импорт сессий Claude Code

Плагин VS Code и CLI пишут одни и те же файлы
`<config>/projects/<encoded-cwd>/<uuid>.jsonl`, где `<config>` — `$CLAUDE_CONFIG_DIR` или
`~/.claude`. Кодирование имени папки (как в CLI 2.1.308, сверено с именами папок
прогонов T0 и с эталоном функции CLI): кодируется реальный путь рабочего каталога
(`process.cwd()`, симлинки раскрыты: `/tmp` → `/private/tmp` на macOS); каждая UTF-16
единица, не являющаяся ASCII-буквой или цифрой, заменяется на `-`; если результат длиннее
200 символов — первые 200 символов, `-` и base36 от модуля 32-битного хэша строки
(`h = (h << 5) - h + unit | 0` по UTF-16 единицам). Так адаптер и зеркало находят
файл по пути. Обратно имя **не декодируется** (`/a/b.c` и `/a/b-c` совпадают),
поэтому рабочий каталог сессии воркер берёт из поля `cwd` в записях jsonl, держит
кэш «файл → cwd» на диске (§5.2) и имя папки использует только как ключ. Подпапки
с транскриптами субагентов и файлы, не являющиеся `<uuid>.jsonl`, игнорируются.
Проверено на 2.1.307: кроме `user`/`assistant` в файле есть записи `attachment`,
`file-history-snapshot`, `api-request*`, `last-prompt`, `ai-title`, `cost-state`,
`queue-operation`, `system` и другие; парсер их пропускает, кроме `ai-title` — его
разбирает отдельно (поле `aiTitle`), адаптер берёт из него заголовок сессии (§8.1).

Формат на 2.1.308 (T15, фикстуры `vscode-takeover-2.1.308` и `adapter-then-outside-2.1.308`,
`docs/notes/t15-questions.md`):

- `claude -p "<промпт>"` (промпт аргументом, как человек в терминале) и `--resume <uuid>` в
  stream-json-режиме адаптера дописывают **один и тот же** файл: обе части несут одни `cwd`
  и `sessionId`, `entrypoint: sdk-cli`, `version`, `gitBranch`. Каждая часть начинается парой
  `queue-operation` (`enqueue`/`dequeue`, без `uuid`), затем запись промпта `user`.
- Каждый блок контента — **отдельная запись** со своим `uuid` (`thinking`, `text`, `tool_use`
  одного ответа модели — три записи с общим `message.id` и полем `apiBlockIndex`); в
  `message.content` записи один блок. `message.stop_reason` есть в jsonl у каждой записи
  ответа: `tool_use` перед вызовом инструмента, `end_turn` у записей последнего ответа хода; в
  stream-json это поле `null`.
- `thinking` в jsonl — пустой текст с `signature`; в stream-json адаптера такой записи в обоих
  прогонах не было (вместо неё — `attachment` `thinking_drop`), поэтому для детекции чужого
  писателя она не считается (§9.3).
- `attachment` (окружение, список инструментов, CLAUDE.md, скиллы) имеют `uuid` и входят в
  цепочку `parentUuid` между `user` и `assistant`; основная цепочка определяется по типу
  записи, а не по `parentUuid`.
- Новые типы без `uuid`: `api-request-shape`, `atis-latch`, `mode`; служебные `cost-state`,
  `last-prompt`. `ai-title` в обоих прогонах 2.1.308 **не записан** — и для промпта
  аргументом (на 2.1.307 был), так что заголовок импортированной сессии чаще всего «Сессия N».
- У записей промпта есть `promptId`, `promptSource: sdk`, `turnOrigin`, `turnPosition`,
  `permissionMode`; у записей CLI-инъекций — `isMeta: true` (парсер такие не показывает),
  у сводки после `/compact` — `isCompactSummary: true`.

### 9.1 Импорт
Кандидаты — `workspace.list_candidates` (§5.3, `GET /api/workers/{id}/candidates`): воркер
обходит `<config>/projects/*/<uuid>.jsonl`, берёт `cwd` первой записи, где оно есть (кэш «файл
→ cwd» на диске, §5.2), группирует по `cwd` с числом сессий и `last_active` (время изменения
самого свежего файла) и отдаёт только папки внутри `allowed_roots`. В клиенте на экране
Workspaces кнопка «Импорт из Claude Code» показывает кандидатов; выбранные папки становятся
workspace проекта через обычный `POST /api/workspaces` с полем `mirror_enabled: true`
(тело `CreateWorkspaceImport`). Хаб шлёт воркеру `mirror.set` (§5.3) — так же для всех
workspace с зеркалом после каждого `hello`; при удалении workspace — `mirror.set` с
`enabled: false`. Воркер принимает только папку внутри `allowed_roots` (§2.1). С 0.23 зеркало
включено у всех workspace по умолчанию (миграция хаба `0011` включила его у существующих), так
что импорт кандидатов — лишь способ добавить папку; на экране Workspaces у каждой папки
переключатель «Сессии VS Code» (`PATCH /api/workspaces/{id} {mirror_enabled}`, §6).

**Без дублей при включении на непустом workspace** (с 0.23). Сессии hqc в папке уже есть в хабе,
а промпты в них — `user.message` хаба со своим `event_id` (v7), не v5 от `uuid` записи, так что
импорт их транскриптов дал бы дубли. Поэтому `mirror.set` с `enabled: true` несёт `sessions?:
[{runtime_session_id, since_ts}]` — сессии хаба в этом workspace с известным транскриптом и время
последнего их события в хабе (не больше 5000, самые свежие; пусто — поля нет; пример
`hub.mirror.set.sessions.json`). Первый проход воркера по такому транскрипту — файл, который
зеркало ещё не читало (смещение 0), до конца файла — не шлёт события записей с `timestamp` <=
`since_ts`; дерево записей и последний промпт при этом строятся как обычно. Неизвестные хабу
транскрипты импортируются целиком, как раньше; уже прочитанные файлы список не трогает.

Импорт — первый проход зеркала по файлу (смещение 0): воркер отдаёт всю историю основной
цепочки событиями §4 через `mirror.event` с исходными `ts` и `event_id` по §3 Event
(`Event::id_from_claude_block`). Маппинг: `user` с текстом — `user.message` (`delivery:
delivered`), `tool_result` — `tool.result`; `assistant` с текстом — `agent.message`, `final:
true` при `stop_reason: end_turn`, `in_reply_to` — последний промпт файла; `tool_use` —
`tool.call`; непустой `thinking` — `agent.thinking`. Записи без событий (`attachment`,
снимки, `api-request*`, `queue-operation`, пустой `thinking`, картинки) пропускаются.

Хаб на неизвестный `runtime_session_id` этого воркера создаёт сессию в проекте workspace:
`cwd` — путь записи относительно workspace, заголовок — `ai-title` (поле `title` кадра), если
есть, иначе «Сессия N» (§3 Session), `system session_created` «Сессия импортирована из Claude
Code». Начальный `locked_by` по флагу `recent` кадра: воркер ставит его, если файл изменён
меньше 30 с назад в момент чтения (часы воркера, не хаба) — тогда `vscode`, иначе `none`.
Автора, которого воркер не знает, ставит хаб: владелец workspace у `user.message`, агент сессии
у остальных. Push по событиям зеркала не шлётся (импорт — сотни старых ответов).

### 9.2 Зеркало
С 0.23 зеркало включено у всех workspace по умолчанию **[решение]** (T21): иначе сессия, начатая
в hqc и продолженная в VS Code, не освобождается, а развилки не видны (вопросы T15 и T20).
На workspace с `mirror_enabled` воркер следит за всеми файлами `<config>/projects/*/<uuid>.jsonl`,
чей `cwd` лежит внутри пути workspace (сравнение по компонентам пути). Опрос раз в **2 с**,
а не уведомления файловой системы **[решение]**: проход — `read_dir` папки проектов и `stat`
каждого файла, читаются только байты после смещения на диске; уведомлений хватило бы не
всегда (FSEvents склеивает события и сообщает каталоги, inotify нужен на каждую папку и не
видит созданное до установки), смещения и пересканирование всё равно нужны, а 2 с — много
меньше 30 с, которые важны для подхвата. Смещение двигается только за обработанные полные
строки; недописанная строка ждёт следующего прохода; файл, ставший короче, читается заново
(дубли гасит `event_id`). Смещения, последний промпт файла и `ai-title` хранятся рядом с кэшем
`cwd` (`$HQC_HOME/mirror/mirror.sqlite3`); `mirror.event` идёт через outbox, как `event`.

Свои записи воркер знает по `uuid`: адаптер Claude Code кладёт в общий реестр в памяти (по
`runtime_session_id`) uuid каждого сообщения `user`/`assistant` основной цепочки из stream-json,
включая эхо `--replay-user-messages` своих промптов, и отмечает, пока процесс сессии жив. Зеркало
свои записи **никогда не эмитит** (их отдал адаптер, в том числе промпт — как `user.message` хаба
со своим `event_id`). Правило для чужих записей:

- процесс hqc этой сессии жив (`locked_by: hqc`) — зеркало **не эмитит** и не двигает смещение
  дальше первой чужой записи; если она остаётся чужой дольше **5 с** (stream-json может
  отставать от файла), это чужой писатель (§9.3);
- процесса нет (`locked_by: vscode` или `none`) — запись эмитится сразу через `mirror.event`;
  с `recent` хаб переводит сессию в `locked_by: vscode` (если была `hqc` — это освобождение,
  §9.3).
- Поскольку адаптер и зеркало выводят `event_id` из одного и того же `uuid` записи,
  стык при переключении `locked_by` в любую сторону гасится уникальным индексом.
  Для записи с несколькими блоками контента правило §3 Event обязательно и для
  зеркала: блок `i > 0` — v5 от `"<uuid>/<i>"`. CLI до сих пор писал один блок на
  запись (все фикстуры и живые прогоны, в том числе 2.1.308), но иначе стык дал бы дубли.

Сессия с `locked_by: vscode` видна в хабе read-only: `state: locked_vscode`, поле ввода закрыто.
В клиенте две плашки: с `held_by` — «Сессия открыта в VS Code … закройте её там» без кнопки
(подхват всё равно `409 vscode_open`); без `held_by` (свежие записи, держателя нет или нет
данных реестра) — «ведётся в VS Code» и кнопка «Подхватить».

### 9.3 Подхват **[решение]**
Правило T15 «30 с тишины в файле» не отличает закрытую сессию от открытой и бездействующей. На
практике (2026-10-23) hqc подхватил открытую в VS Code сессию после 30 с тишины и дописал ходы
через `--resume`; затем пользователь написал в VS Code, и плагин прицепил свой ход к своей
последней записи в памяти, а не к хвосту файла: у записи два потомка, VS Code видит только свою
ветку, 37 записей hqc в его контекст не попали. С 0.22 (T20) подхват решает **держатель**
транскрипта, а развилки, если всё-таки случились, видны в ленте.

**Держатель.** Claude Code (2.1.308) ведёт реестр живых сессий `<config>/sessions/<pid>.json`
(`<config>` — как в §9): `pid` (число; встречался и строкой), `sessionId`, `cwd`, `entrypoint`
(`claude-vscode` у плагина VS Code, `sdk-cli` у `claude -p` и процессов адаптера, есть другие),
`kind`, `status` (`idle` | `busy`), `updatedAt` (мс), `version` и другие поля. Рядом лежат
`<pid>.<hash>.key` — воркер их не читает. Процесс, упавший без уборки, оставляет файл, поэтому
запись живая, только если процесс `pid` существует (`kill -0`). Воркер читает каталог раз в
проход зеркала (2 с; держателей — для всех транскриптов, а не только под зеркалом), исключает
свои процессы — pid агентов и их группы процессов (адаптер запускает CLI лидером группы), а также
запись `sdk-cli` транскрипта, который сейчас ведёт свой процесс (на случай обёртки с другим pid),
— и пропускает незнакомые поля и битые файлы. Остальные записи — держатели; из нескольких на один
транскрипт берётся `busy`, затем самая свежая. Есть ли реестр, воркер сообщает в `hello`
(`capabilities.claude_code.sessions_registry: true`, если каталог существует, §5.4).

- Изменение держателя (появился, исчез, сменил `status`) воркер сообщает хабу отчётом о
  держателе — `session.state` с nil `session_id`, `runtime_session_id` транскрипта и `held_by:
  {entrypoint, status} | null` (§5.4) — не чаще раза в 2 с на транскрипт, через outbox, в одном
  порядке с `mirror.event` (прямой кадр обгонял бы события из outbox со старым `held_by`; так
  провалился первый живой прогон T20). Каждое `mirror.event` несёт держателя, какого воркер видел
  при чтении. На `hello` хаб забывает держателей сессий воркера (`locked_by` не трогает), воркер
  после `hello.ack` сообщает текущих заново.
- Сессия с держателем — `locked_by: vscode` независимо от записей в файл (в том числе импорт
  открытой и бездействующей сессии). Держатель исчез — `locked_by: none` сразу, без 30 с, если
  hqc-процесса по сессии нет (`process_state: stopped`); иначе остаётся `vscode`. При данных
  реестра (`held_by` в `mirror.event`) `recent` сессию не запирает: запись без держателя сделал
  процесс, который уже завершился.
- Держатель появился, пока сессию ведёт hqc: хаб сразу ставит `locked_by: vscode` и пишет `system
  session_released` с `reason: vscode_open` («Сессию открыли в VS Code: hqc остановил агента после
  хода. Чтобы вести её отсюда, закройте её в VS Code и подхватите снова.»), `pending` вводы
  становятся `failed`; воркер останавливает агента после текущего хода (сразу, если хода нет) и
  очищает свою очередь ввода — как при чужой записи ниже.
- Кнопка «подхватить» (`POST /api/sessions/{id}/takeover`). Живой держатель — `409 vscode_open`
  с `message` «сессия открыта в VS Code: закройте её там и подхватите снова» и полем `held_by`.
  Держателя нет: у воркера с реестром подхват проходит сразу; без данных реестра (старый CLI,
  воркер без реестра) действует запасное правило — при `locked_by: vscode` нужна тишина 30 с с
  момента, когда хаб получил последний `mirror.event` с `recent` (поле `vscode_active_at`),
  раньше — `409 vscode_active`. Подхват ставит `locked_by: hqc`, пишет `system session_taken_over`
  («Сессию подхватил hqc. Если она открыта в VS Code, её контекст там устарел: после возврата
  переоткройте сессию в VS Code.») и шлёт воркеру `session.start` с `mode: resume` и
  `runtime_session_id` — uuid файла; адаптер по наличию файла делает `--resume` (§8.1). Воркер
  офлайн — `409 worker_offline`, архив — `409 archived`. Для `locked_by: none` подхват тоже
  проходит, для `hqc` — ничего не делает. Ответ — объект сессии.
- Сообщение в сессию с `locked_by: vscode` **отклоняется** `409 locked_vscode` с полем
  `hint: "takeover"` (и `held_by`, если держатель жив; клиент предлагает «Подхватить» или
  закрыть сессию в VS Code); тихой очереди нет. Воркер на ввод отпущенной сессии отвечает
  `error {code: locked_vscode, retryable: false}`.
- Детекция чужого писателя — запасной путь для писателя, которого реестр не показал (процесс
  короче прохода, нет реестра): учитываются только записи `type: user` и `type: assistant`
  основной цепочки (`isSidechain: false`, не `isMeta`), из которых получается хотя бы одно
  событие (пустой `thinking` не в счёт, §9). Запись с `uuid`, которого адаптер не видел
  в stream-json (и который не является его собственным промптом, §8.1), во время
  работы hqc-процесса означает, что сессию продолжили в VS Code: воркер
  останавливает своего агента после текущего хода (сразу, если хода нет), очередь ввода
  воркера очищается, `session.state` несёт `locked_by: vscode`; хаб пишет `system` с кодом
  `session_released` и `reason: foreign_write` («Сессию продолжили в VS Code: hqc остановил
  агента после хода…»), а `pending` вводы становятся `failed`. Затем зеркало отдаёт придержанные
  записи. Пока hqc-процесс не запущен, любая такая запись с `recent` без данных реестра переводит
  сессию в `locked_by: vscode` (из `hqc` — тоже с `session_released`). `locked_by` из
  `session.state` хаб применяет так: `vscode` воркера побеждает всегда; `vscode` хаба не
  снимается остановкой процесса (`none`) и процессом, который хаб не запускал подхватом (`hqc`);
  иначе — как сообщил воркер. Проверено на 2.1.307 фикстурами T0 (тест
  `t0_stream_and_transcript_share_uuids`) и на 2.1.308 фикстурами T15
  (`t15_two_writers_share_one_transcript`, тесты зеркала `own_records_are_not_foreign`,
  `outside_writer_is_detected`, живой `live_vscode_import_takeover_release`): uuid всех записей
  `user`/`assistant` основной цепочки, включая `tool_result` и эхо промпта, совпадают в
  stream-json и jsonl; при `--resume` stream-json старую историю не повторяет.
- **Развилка.** Писатель, продолжающий не с конца файла (VS Code — со своей последней записи в
  памяти после ходов hqc; `claude --resume <uuid> --resume-session-at <uuid записи>`), начинает от
  более ранней записи вторую линию ходов в том же файле; ходы другой линии в его контекст не
  попадают. Зеркало держит дерево записей транскрипта (`uuid` → `parentUuid` всех записей с
  `uuid`, включая `attachment`, кроме `isSidechain`) и число промптов (записей, дающих
  `user.message`) под каждой записью. Два ребёнка сами по себе — не развилка: параллельные вызовы
  инструментов дают их записи `tool_use` (фикстуры `auto-mode`, `auto-classifier`). Развилка —
  промпт, над которым у какой-то записи есть другой ребёнок с промптами; точка `at_uuid` —
  ближайшая такая запись, `orphaned_turns` — промпты её других детей, `branch_from` — `hqc`, если
  новый промпт свой (реестр uuid адаптера, §9.2), иначе `vscode`. Воркер шлёт через
  `mirror.event` перед событиями нового промпта `system session_forked` (`author: {kind:
  system}`, payload `{text, code, at_uuid, branch_from, orphaned_turns}`, `event_id` — v5 от
  строки `"<at_uuid>/fork"`, одно событие на точку) с текстом «VS Code продолжил с более ранней
  точки: N ходов из hqc не попали в его контекст» (или «hqc продолжил с более ранней точки: N
  ходов из VS Code не попали в его контекст»). Запись попадает в дерево, когда зеркало её прошло
  (придержанная чужая может оказаться своей). После перезапуска воркер строит дерево заново по
  уже прочитанной части файла и старых развилок не повторяет. Хаб хранит событие как обычное
  `system`, клиент рисует строкой с предупреждением. Только для workspace под зеркалом.
  Проверено на фикстуре `fork-2.1.308` (живой прогон T20 без VS Code, тест зеркала
  `fork_is_reported_once`).
- Одновременно сессию ведёт ровно один из двух.

### 9.4 Парсер
Формат jsonl неофициальный и меняется между версиями. Парсер терпит незнакомые типы
записей, логирует их и не падает. Один парсер (`hqc-claude-jsonl`) обслуживает импорт,
зеркало и заголовок адаптера: `Message::is_main`, `stop_reason`, `blocks`, `first_cwd`,
`last_ai_title`. Покрывается фикстурами с реальных файлов (по набору на версию CLI).

## 10. Разрешения

### 10.1 В сессии
`approval.request` — первоклассное событие с кнопками в клиенте. Клиент показывает
**варианты из `options[]` запроса**, с подписями по `canonical`; у Claude Code это
once / session / always / deny, у ACP-агентов — то, что предложил агент. Запрос
уходит **владельцу воркера**; коллега с `write` видит запрос, но ответить не может.
Первый ответ побеждает: он закрывает запрос, событие `approval.response` видят все
устройства, и клиент убирает кнопки. Второй ответ (с другого устройства) получает
`409 request_closed`; события отмены при этом не пишется. Истечение, `POST /stop`,
перезапуск воркера и архивация дают `approval.cancel`, клиент убирает кнопки.
Все эти отмены пишет хаб: при истечении, `stop` и архивации он пишет событие
`approval.cancel` и шлёт воркеру фрейм `approval.response` с вариантом `canonical: deny`,
чтобы адаптер закрыл запрос в рантайме (§5.3); при перезапуске воркера — только событие
(§5.2). При `POST /stop` хаб сначала отменяет открытые запросы с `stopped`, затем шлёт
`session.stop`; адаптер и супервизор воркера при `session.stop` отмену не эмитят (запросы,
открытые к концу прерванного хода, адаптер Claude Code молча забывает). Открытый `clarify`
хаб отменяет так же: событие `clarify.cancel` и фрейм `clarify.response` с
`answers: {}`; адаптер отвечает рантайму `deny`, ход продолжается без ответов.
При `auto_approve` хаб отвечает первым вариантом с `canonical: once`, `by: auto`
(вызовы под `deny` из `[permissions]` воркера до хаба не доходят, §8.1, §14);
режим включает только владелец воркера, в UI подсвечен; на расшаренном проекте он
означает выполнение кода коллегами без подтверждений, UI предупреждает об этом при
включении режима и при выдаче гранта `write`. Push-уведомление на каждый запрос
обязательно (§16).

### 10.2 Вне сессии
У каждого воркера есть служебная сессия (`system_session_id`, §3 Worker), видимая только
владельцу. В неё приходят `worker.approval.request` как события `approval.request` и пишет
логи уровня warn и выше сам воркер. Привязки окружений и профилей не подтверждаются через
хаб вовсе — они меняются только локально (§14).

**Служебная сессия** (с 0.17). Живёт в личном проекте владельца воркера: `owner_id` —
владелец, `worker_id` — воркер, без workspace, `title` — имя воркера (`title_source: user`),
`slug` — `worker-<worker_id>`, агента нет (`runtime: none`, процесс никогда не стартует,
`session.start` ей не шлётся). В объекте сессии (§6) поле `system: true` (передаётся только
`true`); в нумерации «Сессия N» (§3 Session) служебные сессии не считаются. `state` — как у
обычной (§17.1): `worker_offline`, пока воркер не на связи, `waiting`, пока открыт запрос
воркера, иначе `idle`. Ввод, `POST /stop`, `/retry`, `/takeover`, `/archive` и `DELETE` для
неё — `409 system_session`; `PATCH auto_approve: true` — `403`. Клиент показывает служебные сессии не в
списке сессий личного проекта, а отдельной группой «Воркеры» в левой колонке (имя воркера,
«ждёт ответа», «офлайн», непрочитанные); лента — обычная, без поля ввода и кнопок
«Стоп»/«Повторить», с фильтром «только запросы» (карточки `approval.request` и
`clarify.request`).

**Отзыв, замена, удаление** (с 0.21). Отзыв воркера (`DELETE /api/workers/{id}`, §5.1) пишет в
его служебную сессию `system worker_revoked` и архивирует её сам хаб (запрет `/archive` —
только для пользователя); её открытые запросы закрываются `approval.cancel {archived}` без
кадра воркеру — спросивший процесс отрезан. Группа «Воркеры» показывает только
неархивные служебные сессии, то есть неотозванных воркеров; служебные сессии отозванных до
0.21 воркеров архивирует миграция хаба `0009`. Регистрация с заменой (§5.1) разархивирует
служебную сессию, переименовывает её по новому имени и пишет `system worker_replaced`;
удаление отозванного воркера (§6) удаляет её (§17.4).

**Кадры** (§5.3, §5.4; добавлены в 0.17, версия протокола та же):
- worker → hub `worker.approval.request {request_id, kind, description, expires_at}` → `ack
  {}`. `kind`: `workspace.use` (ниже), `workspace.create`, `workspace.delete` (итерация 5,
  §13); список открытый. Хаб пишет в служебную сессию событие `approval.request {request_id,
  tool: <kind>, description, options: [{id: once, canonical: once}, {id: deny, canonical:
  deny}], expires_at}` с `author: {kind: system}` и открывает `PendingRequest` с `kind:
  worker_approval`, `worker_id` воркера; `description` обрезается до 2000 символов,
  `expires_at` — не дальше суток. Повтор кадра с тем же `request_id` (воркер шлёт его снова
  после каждого переподключения, пока ждёт) нового события не пишет; если ответ уже есть,
  хаб после `ack` шлёт его ещё раз.
- hub → worker `worker.approval.response {request_id, option_id}` — ответ владельца или
  `deny` при отмене хабом; воркер отвечает `ack` и тогда, когда запроса у него уже нет. Ответ
  хранится в `PendingRequest.result` до `ack`; не подтверждённый воркером ответ хаб
  досылает после `hello` (`session.start` ему не предшествует).
- `hello.ack` получил необязательное `system_session_id`, `session.start` — `requested_by_owner`
  (передаётся только `true`): хаб ставит его, если workspace сессии добавил владелец воркера.

**Ответ и отмена** — как у `approval` в сессии (§10.1), но ответить может только владелец
воркера (`POST /api/sessions/{system_session_id}/requests/{request_id}` с `option_id`, иначе
`403`); первый ответ закрывает запрос, второй — `409 request_closed`. Истечение
`expires_at` — событие `approval.cancel {timeout}` и кадр `worker.approval.response` с
`deny`. Новый `boot_id` воркера (§5.2) — `approval.cancel {worker_restart}` без кадра: процесс,
который ждал, уже не существует. Push — как на любой `approval.request` (§16).

**Новая папка** (`workspace.use`, с 0.17 — единственное применение до итерации 5). Воркер
хранит кэш папок, в которых соглашался запускать сессии: `$HQC_HOME/known_workspaces.json`
(массив канонических путей, права 0600, запись через временный файл). `session.start` с
`workspace_path`, канонический путь которого не в кэше, для сессии, у которой
`owner_is_worker_owner: false` и нет `requested_by_owner`, воркер не выполняет сразу: шлёт
`worker.approval.request {kind: workspace.use}` с описанием «хаб хочет запускать сессии в
<путь>» и `expires_at` через 10 минут, а `ack` на `session.start` откладывает. `once` —
папка записывается в кэш, ожидающие `session.start` выполняются как обычно; `deny`,
истечение у хаба или своё ожидание `expires_at` + 30 с без ответа — `error {invalid_frame,
retryable: false}` на каждый ожидающий `session.start` (хаб помечает `pending` ввод `failed`
с `system agent_start_failed`, §5.2). Несколько `session.start` в одну папку ждут одного
запроса. Сессии владельца воркера и сессии в workspace, добавленном владельцем, подтверждения
не требуют, и их папка тоже попадает в кэш. Флаги `owner_is_worker_owner` и
`requested_by_owner` — утверждение хаба о личности пользователей, которому воркер доверяет
(§2.1); кэш хаб изменить не может. Так чужой пользователь не запустит сессию в новой папке
без согласия владельца машины (аудит, A2, частично).

**Логи воркера.** События `tracing` уровня `WARN` и `ERROR` воркера (кроме строк самого
пересыльщика) идут в служебную сессию событием `system {text, code: worker_log, level:
warn|error}` с `author: {kind: system}`, через outbox, как остальные события (§5.2); `text` —
`<target>: <сообщение> <поля>`, до 2000 символов. Сессию воркер узнаёт из `hello.ack`;
строки до первого `hello.ack` ждут в памяти (до 60). Частота: одинаковый текст — не чаще
раза в секунду, всего — не больше 60 строк в минуту (окно в 60 с от первой строки);
отброшенное считается и сообщается одной строкой `пропущено N` (`level: warn`), как только
лимит позволяет, — она входит в те же 60. Строки `worker_log` не считаются непрочитанными
(исключение из правила §6), push на них нет. Клиент показывает их моноширинной строкой со
временем (до секунд), уровнем и текстом как есть, без Markdown.

## 11. Доступ и шаринг

Модель Google Docs: всё приватно, Grant даёт доступ. Функция
`can(user, action, resource)` стоит на каждом запросе к хабу с первого дня.

| действие | view | write | manage | владелец проекта |
|---|---|---|---|---|
| читать историю, артефакты | да | да | да | да |
| писать в сессию, прикладывать файлы | | да | да | да |
| создавать сессии в проекте | | да | да | да |
| остановить ход, steer | | да | да | да |
| отвечать на `clarify` | | да | да | да |
| `hqc_send`/`hqc_ask` в сессию (через своего агента) | | да | да | да |
| `hqc_schedule` в сессию | | да | да | да |
| отвечать на `approval` | | | | только владелец воркера |
| переименовать, архивировать, разархивировать, удалить сессию | | | да | да |
| создавать/удалять workspace | | | да (с подтверждением владельца воркера) | да |
| выдавать гранты | | | да | да |
| удалить проект | | | | да |
| менять окружение и профиль workspace | | | | только владелец воркера, локально |

- Грант на проект распространяется на все его сессии; грант на сессию — только на неё.
- Воркеры не шарятся. Коллега получает доступ к машине только через workspace
  расшаренного проекта, внутри его пути.
- Агент действует с правами владельца сессии.
- Отзыв гранта: текущий ход не прерывается, следующий ввод отклоняется, подписка
  клиента закрывается.
- Персональный проект не шарится. Несколько агентов разных пользователей в одной
  сессии — запрещено.
- Организаций и ролей нет.

### 11.1 Кто платит и чужие сессии **[решение]**
- **Все рантаймы на воркере** (Claude Code, Hermes, любой ACP-агент) работают
  с локальными учётными данными машины, то есть платит **владелец воркера**, кто бы
  ни создал сессию. Передавать ключи коллеги на чужую машину нельзя: владелец
  машины их увидит.
- **Голая модель** — ключи владельца сессии (`owner_id`) в хабе.
- Шаринг проекта с workspace на воркере означает «одалживаю свои учётные данные»;
  при выдаче гранта `write`/`manage` UI говорит это явно. Владелец воркера может
  запретить чужие сессии флагом `allow_foreign_sessions: false` (локальный конфиг,
  виден хабу через `hello`); флаг не запрещает чужой ввод в сессии самого
  владельца — это покрывается предупреждением при выдаче гранта.
- Чужая сессия (`owner_is_worker_owner: false`) на ACP-агенте с `isolation: none`
  отклоняется воркером. Чужая сессия на Hermes получает профиль, указанный
  в привязке как `foreign_profile`; если его нет — отклоняется: иначе коллега
  получил бы долгосрочную память владельца (Hindsight) на чтение и запись.
- Событие `usage` пишется, где рантайм его отдаёт; для ACP-агентов без usage
  расход по сессии в UI показывается как «нет данных».

## 12. Артефакты

Хранилище: диск хаба (`HQC_ARTIFACT_DIR`, файл `<dir>/<sha256[0..2]>/<sha256>`; S3 —
позже), ключ по sha256, содержимое одно на хэш. Типы: file, image, diff, html, text.
Лимит артефакта 100 МБ (поток пишется во временный файл с подсчётом sha256, превышение —
`413 too_large`, файл удаляется). Запись — §3 Artifact; повторная загрузка того же файла
тем же пользователем под тем же именем возвращает прежнюю запись.

`kind` при загрузке: явное поле `kind` клиента; иначе по типу из multipart (пустой и
`application/octet-stream` угадываются по расширению): `image/*` → image; `.diff`,
`.patch`, `text/x-diff`, `text/x-patch` → diff; `text/html` → html; прочие `text/*` → text;
остальное → file.

Ссылки. События хранят только `artifact_id`; клиент при рендере запрашивает
`GET /api/artifacts/{id}/url` и получает `{url, expires_at}`: `<база>/artifacts/{id}?exp=<unix
s>&sig=<base64url HMAC-SHA256 от "{id}.{exp}">`, TTL 10 минут. База —
`HQC_ARTIFACT_PUBLIC_BASE` (публичный домен `artifacts.<hub-domain>` на тот же хаб, вне
Cloudflare Access); не задана — ссылка относительная, на домен хаба (за Access). Ключ —
`HQC_ARTIFACT_KEY` или случайный на запуск. `GET /artifacts/{id}` без подписи или с
неверной — `403`, просроченная — `410`; клиент на `403`/`410` запрашивает ссылку заново
(для `<img>` — один раз по `onerror`). Ссылку получает только владелец артефакта (`404`
остальным); сама ссылка — право доступа, cookie не нужны.

Заголовки отдачи (и по ссылке, и воркеру): `Content-Security-Policy: sandbox;
default-src 'none'; img-src data:; style-src 'unsafe-inline'; frame-ancestors 'none'`,
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
`Cache-Control: private, max-age=600` (воркеру `private, no-store`), по ссылке ещё
`Access-Control-Allow-Origin: *` и `Cross-Origin-Resource-Policy: cross-origin` (клиент
читает дифф и текст через `fetch`). `Content-Type` по `kind`: image — `mime`, если он
`image/*`; text и diff — `text/plain; charset=utf-8`; html — `text/html`; file —
`application/octet-stream`. `Content-Disposition` (`filename` и `filename*=UTF-8''…`):
image, text, diff — `inline`, file — `attachment`, `&dl=1` — всегда `attachment`. HTML
`inline` — только если запрос пришёл на хост `HQC_ARTIFACT_PUBLIC_BASE`: тогда CSP
`sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src
'unsafe-inline'; img-src data:; font-src data:` без `X-Frame-Options`, и клиент
рендерит его в iframe `sandbox="allow-scripts"` без `allow-same-origin` — страница без
сетевых запросов, не видит cookie и API хаба. На домене хаба HTML — всегда `attachment`
со `sandbox` CSP без скриптов, а клиент показывает ссылку «Открыть». На хосте
`HQC_ARTIFACT_PUBLIC_BASE` хаб отдаёт только `/artifacts/*` (и `/health`), остальное —
`404`; в CSP самого хаба (§20) этот origin добавляется в `img-src`, `frame-src` и
`connect-src`.

Воркер качает артефакты по `GET /worker/artifacts/{id}` своим токеном (§5.3), без TTL:
только артефакты, пришедшие во вводе сессии этого воркера (остальным — `404`); имя и
`kind` — в заголовках `x-hqc-artifact-name` (percent-encoded) и `x-hqc-artifact-kind`.

Клиент. Пользователь → агент: файлы прикладываются к сообщению (скрепка, перетаскивание,
вставка; несколько; превью картинок как `data:`-URL), сначала каждый `POST /api/artifacts`,
потом ввод с `artifact_ids` (текст может быть пустым); повтор неудачной отправки не
загружает уже загруженное. Воркер кладёт их в `.hqc/inbox/` и подставляет пути (§8.1);
картинки для рантаймов с vision дополнительно отдаются как изображение. В ленте
вложения `user.message` и события `attachment` рисуются одинаково: image — inline, diff —
блоком кода с подсветкой добавленных и удалённых строк (до 512 КБ, больше — карточкой),
html — iframe с домена артефактов или ссылка «Открыть», text и file — карточка с именем,
размером и кнопками «Открыть» (кроме file) и «Скачать». Агент → пользователь:
`hqc_attach` (итерация 3); диффы ACP-агентов адаптер сохраняет артефактом сам (§8.2).
Загрузка воркером (`PUT /worker/artifacts`, §5.4) — вместе с `hqc_attach`.

**Уборка** (с 0.23, T21). Раз в сутки (первый раз — сразу после старта) хаб удаляет записи
артефактов, на которые не ссылается ни одно событие (`user.message.artifact_ids`, `artifact_id`
у `attachment` и `tool.result`) и которые старше `HQC_ARTIFACT_RETENTION_DAYS` (по умолчанию 30,
`0` — не удалять) по `updated_at` — последней загрузке того же файла или вводу с ним. Файл с диска
удаляется, только когда на его sha256 не осталось записей: сначала он переносится в сторону, затем
хаб снова проверяет записи и при появившейся (загрузка того же файла в этот момент) возвращает
его; загрузка, в свою очередь, кладёт файл на место после записи строки, если его нет. Записи
`artifact_sessions` уходят вместе с артефактом. Квот на пользователя нет.

## 13. Жизненный цикл workspace

### 13.1 Создание
`dir` (существующая папка), `clone` (git clone в новую папку), `worktree` (git worktree
от существующего workspace на ветку). Только внутри `allowed_roots`, с подтверждением
владельца воркера через служебную сессию (§10.2), кроме случая, когда он сам
инициатор.
С 0.16 реализован `dir` (`POST /api/workspaces`, §6): папку выбирают в клиенте по дереву
`fs.list_dirs` или вводят путь руками, воркер проверяет её `fs.stat` (§5.3), хаб хранит
канонический путь. Добавлять workspace на воркер может только его владелец (до шаринга
итерации 6 других пользователей у воркера нет), поэтому подтверждения через служебную
сессию пока нет; воркер офлайн — workspace не создаётся. `clone` и `worktree` — итерация 5.

### 13.2 Удаление
`dir` — удаляется только запись в хабе, папка не трогается; пока в workspace есть
неархивные сессии — `409 workspace_in_use` (§6), архивные остаются без workspace. `clone` и `worktree`
удаляются с диска только при `created_by_hqc: true`: `worktree` — через
`git worktree remove`, `clone` — удаление папки. Перед удалением воркер проверяет
незакоммиченные изменения и непушенные коммиты; при их наличии запрос подтверждения
содержит предупреждение. `ephemeral` workspace при архивации последней сессии
**не удаляется автоматически**, а помечается «к удалению» и показывает кнопку;
удаление всегда с подтверждением.

### 13.3 Шаблон сессии проекта
Необязательная настройка проекта: `{workspace_id, cwd_pattern: "<slug>", prompt}`.
Новая сессия по шаблону создаёт подпапку `<workspace>/<slug>` и начинает со
стартового промпта. Workspace в шаблоне обязателен. Для проектов типа cad и KiCad,
где сессия соответствует детали или плате.

### 13.4 Выбор workspace
При создании сессии из UI workspace выбирается явно (в форме заранее выбран
`default_workspace_id` проекта, `cwd` — необязательная подпапка); `hqc_spawn` и крон требуют
`workspace` или используют `default_workspace_id` проекта; без того и другого —
ошибка (`409 no_workspace` в REST, §6).

## 14. Локальный конфиг и окружения воркера

Локальный конфиг воркера — единственный источник истины для:

- `allowed_roots[]` — единственное, что воркер знает о workspace: любой workspace из
  `session.start` и любой путь `fs.*` должны лежать внутри (§5.3). Блока `[workspace]`
  в `worker.toml` с 0.16 нет: workspace создаются в хабе (§3, §13.1); блок итерации 1 в
  старом файле игнорируется с предупреждением в логе при старте;
- `environments{}` — именованные окружения;
- `env_bindings[]` — записи `{path, environment, hermes_profile?, foreign_profile?}`.
  Привязка ищется **по пути workspace** (не по `cwd` сессии), берётся самая длинная
  совпадающая, иначе `default`. `environment` из `session.start` только сверяется;
- `acp_agents{}` — `{name: {command: <абсолютный путь>, args[], isolation:
  verified|none}}`;
- `allow_foreign_sessions`, `share_local_models`;
- `max_sessions` (процессов агентов одновременно, по умолчанию 8) и `insecure_http`
  (`http://` к хабу не на loopback, §5.1);
- `[permissions]` — политика разрешений Claude Code (ниже; в `hello` пока не
  передаётся).

Хаб получает копию в `hello` и показывает её; менять может только владелец воркера
на машине (`hqc-worker env ...`).

Политика разрешений `[permissions]` (действует с 0.14 для всех сессий Claude Code воркера;
окружения итерации 5 смогут её дополнять через `settings`):

```toml
[permissions]
mode = "ask"     # "ask" | "auto"
allow = ["Bash(cargo test:*)", "Read"]   # выполнять без вопроса
deny = ["Bash(sudo:*)", "Bash(git push:*)"]  # никогда не выполнять и не спрашивать
```

- `mode = "ask"` (по умолчанию): вызовы вне обоих списков спрашиваются (`approval.request`);
  `mode = "auto"`: `--permission-mode auto`, CLI решает сам и не спрашивает никогда (§8.1),
  граница — только `deny`; воркер пишет предупреждение в лог при старте;
- `allow` по умолчанию пуст;
- `deny`, если поля (или блока) нет: `Bash(sudo:*)`, `Bash(ssh:*)`, `Bash(scp:*)`,
  `Bash(rm -rf /*)`, `Bash(curl * | sh)`, `Bash(curl * | bash)`, `Bash(dd:*)`, `Bash(mkfs*)`,
  `Bash(git push --force:*)`, `Bash(git push -f:*)`; `deny = []` его отключает
  **[решение]**;
- правило — `Инструмент` или `Инструмент(содержимое)`: имя из латиницы, цифр и `_`
  (`mcp__hqc`, допустим `*` в конце), непустое содержимое в одной паре скобок в конце
  правила, не длиннее 256 байт, без управляющих символов. Неверное правило или неизвестное
  поле — ошибка чтения конфига: CLI в `-p` молча игнорирует настройки, которые не прошли
  его проверку, и одно плохое правило сняло бы весь `deny`.

Три уровня, от сильного к слабому: `deny` воркера (не выполняется, не спрашивается, `always`
и `auto` его не отменяют) → `allow` воркера и правила `always` из `settings.local.json`
(выполняется без вопроса) → всё остальное (спрашивается владельца в `ask`, решает
классификатор CLI в `auto`).

Окружение определяет, с чем запускается процесс агента (Claude Code или ACP-процесс —
оба запускаются воркером):

- `ssh_keys`: ключи, выдаваемые через отдельный сокет ssh-agent только этому
  процессу; по умолчанию агента нет;
- `env`: переменные и токены (GitHub и т.п.);
- `settings`: дополнительные настройки Claude Code через `--settings` (например,
  `permissions.deny` для `Bash(ssh*)`, `Bash(scp*)`); **только для Claude Code**,
  у ACP-агентов аналога нет, поэтому для них окружение `default` слабее: граница —
  только отсутствие ключей;
- `allow_local_mcp`: разрешить MCP-серверы с машины (Claude Code: без
  `--strict-mcp-config`; Hermes: без `HERMES_ACP_SKIP_CONFIGURED_MCP`); по умолчанию
  false;
- `network`: политика для песочного режима bash Claude Code, если включён;
- `roots`: дополнительные разрешённые пути;
- `launch`: `process` (единственное значение в первой версии; `os-user` и `container`
  зарезервированы).

Окружение `default`: нет ключей, нет токенов, `deny` из `[permissions]` (по умолчанию в
нём и ssh/scp), локальные MCP выключены. Ключи одного проекта (например `infra`) выносятся из
`~/.ssh` в хранилище воркера (Keychain на маке) и доступны только сессиям путей
с этим окружением.

Ограничение: без контейнера или отдельного пользователя ОС агент видит файлы
и окружение процессов пользователя, включая чужие workspace и токены сессий на той же
машине. Граница — отсутствие ключей, а запреты в настройках — первая линия,
не граница. Windows в первой версии: только `env` и `settings`, без `ssh_keys`.

## 15. Поиск

Postgres: `tsvector` с конфигурацией `simple` (смешанный русский и английский текст)
плюс `pg_trgm` для fuzzy по `event.payload.text` и названиям сессий. Результаты
фильтруются по грантам. Ограничение: у `simple` нет стемминга, словоформы находит
только триграммный поиск. Один индекс, два потребителя: строка поиска в клиенте
и `hqc_search_history`.

## 16. Уведомления и крон хаба

Web Push на события: `approval.request`, `clarify.request`, `worker.approval.request`
(владельцу воркера; с 0.17 это событие `approval.request` в служебной сессии воркера,
§10.2: `title` — имя воркера, `tag` — `<system_session_id>:<request_id>`; на строки
`worker_log` push нет); финальный `agent.message`, `peer.message` и `system` о
недоставленном вводе (кроме событий зеркала: на них push нет вовсе, §9.1) — владельцу сессии и пользователям с грантом, которые писали
в эту сессию, если у них нет активной WS-подписки на неё. На iOS Web Push работает
только из установленного PWA — ограничение первой версии. Мост в Telegram —
опционально, через `hermes send`.

Тело push (JSON, `hqc_proto::api::PushMessage`, пример `examples/wire/api.push.json`):
`{session_id, type, title?, body?, tag?, payload?}`, где `type` — тип события,
`payload` — само событие §4 как хранится. Хаб кладёт `title` (название сессии), `body`
(краткий текст), `tag` (`<session_id>:<request_id>` для запросов, иначе
`<session_id>:<type>`: уведомление с тем же тегом заменяет предыдущее) и опускает
`payload`, если сообщение не влезает в push (около 4 КБ). Сервис-воркер клиента без
`title`/`body` строит их по `type` и `payload`, показывает `approval.request` и
`clarify.request` с `requireInteraction`, по клику открывает `#/s/<session_id>`.

Крон хаба: `ScheduledMessage` — в `at` или по `cron` в `timezone` пользователя
отправить `message` в `session_id`, либо создать сессию по шаблону проекта
в `workspace_id` и отправить туда. Пропущенные запуски (хаб лежал): при `catch_up`
выполняется один раз, иначе пропускаются. Никакого планировщика задач для агентов;
всё сложнее — крон Hermes.

## 17. Состояния и жизненный цикл

### 17.1 Состояние сессии
`state` вычисляется хабом при отдаче из `archived`, `locked_by`, статуса воркера,
открытых запросов, `process_state` и доставки. Приоритет сверху вниз, первое истинное;
отдельно отдаётся `queue_len` — число вводов в `pending`:

| state | когда |
|---|---|
| `archived` | архив |
| `locked_vscode` | `locked_by: vscode` |
| `worker_offline` | воркер недоступен |
| `waiting` | есть открытый `approval`/`clarify` |
| `error` | есть ввод с `delivery: failed` или последний ход завершился ошибкой процесса |
| `running` | идёт ход |
| `queued` | `queue_len > 0`, хода нет (агент поднимается) |
| `idle` | иначе |

Событие `status.state` использует тот же набор.

Клиент показывает ход по `state` (из `summary`/`session.summary` и объекта сессии), без
отдельных событий: `running` — индикатор в шапке и строка «агент работает» внизу ленты
(«выполняет <tool>», пока у последнего `tool.call` нет `tool.result`), `queued` — «ввод в
очереди», `waiting` — «ждёт подтверждения». Событие `status` строкой ленты не рисуется,
кроме `error` с `detail`.

«Идёт ход» хаб ведёт сам: ход открывается `ack` воркера на `session.input` (воркер
передаёт ввод рантайму по одному на ход, §17.2) и закрывается `agent.message` с
`final: true`, `status` с `idle` или `error` (последний даёт «ход завершился ошибкой»),
остановкой процесса или сторожевым таймером (§17.3, тоже «ход завершился ошибкой»).
«Ход завершился ошибкой» держит `error` до следующего ввода: новый `user.message`
сбрасывает признак. `worker_offline` — у сессии есть воркер и он не подключён сейчас.

### 17.2 Ввод во время хода **[решение]**
Ввод из очереди ввода (§7.1), пришедший во время хода, ждёт финального ответа
и запускает следующий ход; один ход на каждый элемент, в порядке `seq`. Кнопка
«прервать и отправить» делает `session.stop` и затем ввод. Для рантаймов с `steer`
(Hermes) доступна кнопка «вмешаться»: `session.steer` без прерывания. Два пользователя
с `write` — та же очередь.

### 17.3 Процессы
- Простаивающий агент по умолчанию не трогается. `idle_timeout` воркера > 0 —
  процесс завершается, следующий ввод поднимает его через resume.
- Воркер офлайн: ввод копится в хабе (`pending`), сессия `worker_offline`,
  доставка при подключении в порядке `seq`. Открытые `approval` на офлайн-воркере
  остаются открытыми до его возвращения или `expires_at`.
- Перезапуск воркера хаб узнаёт по новому `boot_id` в `hello` (§5.2): все агенты
  `stopped`; открытые `approval`/`clarify` получают `approval.cancel`/`clarify.cancel
  {worker_restart}`; незавершённый ход теряется, хаб пишет `system turn_lost`;
  `pending` вводы досылаются после `hello` (через `session.start` с `mode: resume`).
  Переподключение с тем же `boot_id` — не перезапуск, ничего не отменяется.
- Процесс агента, завершившийся в первые 500 мс после запуска, считается неудачным
  стартом: `start`/`resume` адаптера возвращает ошибку (воркер отвечает
  `agent_start_failed`, retryable, §5.2), а не «процесс завершился» — иначе воркер с
  непустой очередью поднимал бы его по кругу. Процесс, умерший позже с ошибкой или
  посреди хода, даёт `system agent_exited`; воркер поднимает его через `resume`, если в
  очереди есть ввод.
- Перезапуск хаба: воркеры переподключаются, досылают outbox; `PendingRequest`
  восстанавливаются из базы, недоставленные `mcp.result` досылаются.
- Сторожевой таймер хода **[решение]**. Если сессия в `running` (§17.1), а от её воркера по
  ней нет ни одного события, включая `agent.delta`, дольше `HQC_TURN_WATCHDOG_S` (по
  умолчанию 900 с, `0` выключает), хаб считает ход потерянным: открытые
  `approval`/`clarify` отменяет с `timeout`, закрывает ход без финального сообщения
  (ввод остаётся `delivered`), пишет `system turn_lost` с текстом «no events for N s», и
  сессия показывает `error` до следующего ввода. Отсчёт идёт от последнего события
  воркера или от момента, когда сессия снова стала `running`: ожидание ответа
  пользователя (`waiting`) и офлайн воркера (`worker_offline`) в него не входят. Время
  событий хаб держит в памяти; после перезапуска хаба каждый открытый ход получает полный
  срок. Воркеру хаб ничего не шлёт: процесс и его очередь ввода не трогаются.

### 17.4 Архивация и удаление
- Архивация: хаб шлёт `session.kill`, открытые запросы получают
  `approval.cancel`/`clarify.cancel {archived}`, `pending` вводы помечаются `failed`,
  буфер send очищается. Разархивация возвращает `idle`; процесс поднимется через
  resume по первому вводу.
- Удаление сессии: события, `ReadCursor`, `PendingRequest`, артефакты сессии
  (если на них не ссылается другая сессия) удаляются; файлы jsonl на воркере
  **не трогаются**; поздние события из outbox воркера получают `ack` и отбрасываются
  (§5.2).
- Уборка на воркере (с 0.23, T21). При архивации и удалении сессии (и её проекта) хаб шлёт воркеру
  после `session.kill` кадр `session.cleanup {session_id, workspace_path | null, cwd, event_ids[]}`
  → `ack` (пример `hub.session.cleanup*.json`; добавлен только добавлением, `session.kill` не
  менялся): `event_ids` — вводы сессии с вложениями. Воркер удаляет
  `<workspace>/<cwd>/.hqc/inbox/<event_id>` этих вводов, а у сессии без workspace (`null`, §8.4) —
  её папку `<scratch_root>/<session_id>`. Воркер не доверяет путям хаба (§2.1): workspace —
  внутри `allowed_roots`, `cwd` — относительный без `..` и раскрывается внутри workspace, `.hqc` и
  `inbox` — настоящие каталоги, не символические ссылки; удаляются только прямые дети
  `.hqc/inbox` с именем-uuid события и только `<scratch_root>/<uuid>`, символическая ссылка там
  удаляется как ссылка. Ничего вне `.hqc/inbox` и `scratch_root` воркер не удаляет. Воркер офлайн
  — кадр не досылается; это покрывает уборка при старте: inbox-папки (дети `.hqc/inbox` с именем
  uuid) старше 14 дней по времени изменения в известных воркеру workspace —
  `known_workspaces.json` и рабочие каталоги, куда он писал вложения
  (`$HQC_HOME/inbox_dirs.json`), только внутри известного workspace и `allowed_roots`.
- Удаление воркера (`DELETE /api/workers/{id}?purge=1`, §6; только отозванного и без
  неархивных сессий): его служебная сессия удаляется как сессия выше, его workspace-записи —
  как §13.2 (архивные сессии теряют `workspace_id` и `worker_id`, история остаётся), затем
  запись воркера. Файлы на машине не трогаются.

## 18. Стек

- Hub: Rust, axum, tokio, sqlx, Postgres. Артефакты — диск или S3.
- Worker: Rust, один статический бинарник на macOS/Linux/Windows, systemd/launchd/
  служба Windows, опциональная иконка в трее. MCP-сервер на `rmcp` (подкоманда
  `hqc-worker mcp`). ACP-клиент — крейт `agent-client-protocol` (официальный Rust SDK
  протокола) **[проверить]** актуальность. Secure store для токенов и ключей: Keychain
  на macOS; на Linux и Windows в первой версии токен воркера — файл 0600 (§5.1),
  libsecret и DPAPI позже.
- Client: TypeScript, адаптивный веб, PWA; Tauri на том же коде позже.
- Общие крейты: `hqc-proto` (схема событий и фреймов, версионируется),
  `hqc-claude-jsonl` (парсер транскриптов), адаптеры — отдельные крейты.

## 20. Хостинг и безопасность

- Хаб слушает только интерфейс туннеля; `/api/*` за Cloudflare Access с проверкой
  JWT; `/worker/*` вне Access, только токены воркеров, rate limit на enroll;
  `artifacts.<hub-domain>` публичный, только подписанные ссылки с TTL.
- Dev-режим хаба (`HQC_DEV=1`, без Access) допускается только на loopback-адресе
  `HQC_HUB_LISTEN` и без `HQC_ACCESS_*`; иначе хаб не стартует (§6).
- Токены воркеров — случайные 256 бит, в базе только хэш; отзыв из UI.
- `Origin` **[решение]**: WebSocket-апгрейд `/api/ws` без `Origin` или с `Origin`, не
  совпадающим с `Host` запроса, — `403`; не-GET запросы `/api/*` с чужим `Origin` — `403`
  (без `Origin` — пропускаются: так ходят не-браузерные клиенты). Совпадение — схема
  `https`, либо `http` для loopback-хоста (dev), хост и порт равны `Host`. Защита от
  cross-site WebSocket hijacking и CSRF при cookie Access с `SameSite=None`; в Access
  дополнительно SameSite Lax (RUNBOOK §1.6).
- Заголовки на всех ответах хаба: `Content-Security-Policy: default-src 'self';
  connect-src 'self' wss: https:; img-src 'self' data:; style-src 'self' 'unsafe-inline';
  object-src 'none'; base-uri 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. Сборка клиента
  без inline-скриптов (проверяет тест клиента). HSTS ставит Cloudflare.
- Лимиты (в памяти процесса хаба; адрес — `CF-Connecting-IP`, иначе адрес соединения):
  `POST /worker/enroll` — 10 в минуту и 10 живых неподтверждённых кодов на адрес, 1000
  всего; `POST /worker/enroll/poll` — 60 в минуту на адрес; `/worker/ws` — 20 неверных
  токенов в минуту на адрес (дальше `429` без запроса в базу), токен не той формы в базу
  не идёт, не больше 16 проверок токена одновременно (`503`); сообщения WebSocket клиента и
  воркера — до 1 МиБ, очередь отправки воркеру ограничена (переполнение рвёт соединение,
  состояние досылается из базы после `hello`). Поверх — правило Rate Limiting Cloudflare
  WAF на `/worker/*` (RUNBOOK §1.6).
- Push: хаб шлёт POST на `endpoint` подписки, поэтому принимаются только `https://` без
  userinfo и нестандартного порта на хостах push-сервисов: `fcm.googleapis.com`,
  `updates.push.services.mozilla.com`, `*.push.services.mozilla.com`, `*.push.apple.com`,
  `*.notify.windows.com`; редиректы при отправке не выполняются.
- JWKS Access: ключи обновляются вне блокировки кэша, при ошибке обновления остаётся
  прежний набор, повторные попытки с нарастающей паузой (5 с … 5 мин).
- Воркер: `hub_url` только `https` (§5.1), окружение агента — белый список (§8.1), outbox —
  каталог 0700, файлы 0600.
- `api_keys` пользователей шифруются мастер-ключом из env хаба.
- Cloudflare Tunnel: лимит тела запроса ~100 МБ (совпадает с лимитом артефакта),
  долгие соединения — heartbeat и переподключение.
- Бэкап: Postgres и хранилище артефактов; outbox воркеров переживает перезапуск хаба.

## 21. Риски

- Формат jsonl Claude Code и протокол stream-json/control неофициальные; держать
  парсер и адаптер терпимыми, покрыть фикстурами, фиксировать версию CLI.
- Подхват опирается на общий файл сессии у плагина и CLI; смена хранилища плагином
  ломает зеркало.
- ACP у Hermes стабилен, но методы ACP v2 (`session/resume`, `session/fork`) ещё
  черновик; адаптер держится на v1 плюс `session/load` и фиксирует хэш коммита
  Hermes (`4787e4d5` на llm-server).
- Граница между сессиями на одной машине без контейнера мягкая (§14); для
  ACP-агентов кроме Hermes она ещё слабее (§2.1).
- Цепочки агент→агент ограничены таймаутами и бюджетами, а не семантикой; при
  злоупотреблении `ask` деньги тратятся до лимита.

## 22. Аналоги и заимствования

Проверены на 2026-10-22.

- **Codync** (Rust-хост на каждой машине, ACP к 40+ агентам, SQLite, iPhone/Electron/TUI,
  Cloudflare-relay с E2E). Ближе всего по духу: боты с папкой и политикой разрешений,
  групповые чаты с @ и лимитом в 3 раунда, встроенный `team` MCP для вопросов другим
  ботам. Архитектура обратная нашей: много хостов, клиент подключается к каждому.
  Нет веба и Android, зеркала VS Code, шаринга, общего поиска и очереди при офлайне.
- **Paseo** (TS-демон, Expo-клиенты, relay). Зрелее по клиентам, без Hermes и без
  одного хаба над многими машинами.
- **Claude Code Remote Control** — официально, только Claude Code, без проектов
  и Hermes.
- **CloudCLI / claudecodeui** — одна машина, читает `~/.claude/projects`; единственный
  аналог с зеркалом сессий VS Code.
- **Agent Host Protocol (Microsoft, MIT)** — протокол «хост между многими клиентами
  и ACP-агентами»: действия с `serverSeq`, реконнект по `lastSeenServerSeq`,
  write-ahead с эхом `origin`, «первый `toolCallConfirmed` побеждает», один ход
  на чат. Это ровно наш §5–§6 и §17, но без воркеров, пользователей, грантов,
  агент→агент и хранения. Целиком не берём; взяты: эхо `client_op_id` (§6), правило
  первого ответа на approval (§10.1), словарь действий при именовании событий.
  Совместимый AHP-фасад над `/api/ws` возможен позже, если появятся сторонние клиенты.
- **OpenAB / OpenACP** — мосты ACP-агентов в Discord, Telegram, Slack. Запасной UI:
  если веб-клиент задержится, служебный бот в Telegram с темами форума покрывает
  уведомления и ответы на approval. В ТЗ не входит.

### 22.1 Отвергнутая альтернатива: без хаба
Модель Codync — каждый воркер сам хост, клиент подключается ко всем. Отвергнута,
потому что `ask`/`send` между машинами, общая история и поиск, шаринг коллегам,
очередь ввода при офлайн-воркере и один адрес для push требуют общего состояния;
без хаба каждую из этих вещей пришлось бы делать peer-to-peer.
