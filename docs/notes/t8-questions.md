# T8 — Docker-образ hqc-hub и сборка в ghcr.io: решения и открытые вопросы

Задача делалась без человека: Dockerfile и compose проверены локально на home-mac
(OrbStack, linux/arm64, нативно), workflow `image.yml` — только `actionlint`, в GitHub он
ещё не запускался (push и настройки пакета — за человеком). `docs/SPEC.md` не менялся:
хаб в контейнере слушает `0.0.0.0` внутри своей сети, а наружу виден только через
туннель — это то же правило §20 («только интерфейс туннеля»), раздача клиента хабом
описана в RUNBOOK §1.7, не в спеке.

## Dockerfile

1. **Debian trixie во всех стадиях** (`rust:1-slim-trixie`, `node:22-trixie-slim`,
   `debian:trixie-slim`). Хаб линкуется с системным OpenSSL: `web-push` → `ece` →
   `openssl-sys` (rustls только у reqwest и sqlx). Сборка и рантайм на одном релизе Debian —
   чтобы glibc и `libssl3t64` гарантированно совпадали. В рантайме поэтому кроме
   `ca-certificates` есть `libssl3t64`.
2. **`rust:1`, а не фиксированная версия**: соответствует `channel = "stable"` в
   `rust-toolchain.toml` и `dtolnay/rust-toolchain@stable` в CI (на 2026-10-22 — 1.99.1).
   Сам `rust-toolchain.toml` в контекст сборки не попадает (`.dockerignore`): toolchain
   образа называется `1.99.1-<triple>`, а не `stable`, и rustup стал бы качать второй.
   Минус — образ на CI может собраться компилятором новее, чем был в прошлый раз. Если
   нужна воспроизводимость, зафиксировать `rust:1.99-slim-trixie` и поднимать руками. Вопрос.
3. **Кэш зависимостей — заглушки крейтов, а не `--mount=type=cache`.** `cache-to: type=gha`
   сохраняет слои, но не содержимое cache mount'ов; на чистом раннере GitHub такой кэш был
   бы пустым всегда. Слой «зависимости, собранные по `Cargo.toml`/`Cargo.lock` с пустыми
   `lib.rs`/`main.rs`» кэшируется в gha и пересобирается только при смене манифестов.
   После копирования настоящих исходников `touch` всех `*.rs` — иначе cargo может счесть
   заглушку новее (COPY сохраняет mtime из контекста). Без cargo-chef: лишний сторонний
   образ/бинарник ради четырёх крейтов не нужен. При добавлении крейта в workspace его
   `Cargo.toml` надо добавить в Dockerfile отдельной строкой `COPY` — иначе сборка упадёт
   сразу (cargo не найдёт члена workspace), молча это не сломается.
4. **Клиент собирается на `$BUILDPLATFORM`**: результат — статические файлы, при
   кросс-сборке нет смысла гонять node под эмуляцией. Node 22, а не 20: `vitest` 5 требует
   22+, `vite` 8 — 20.19+; CI-job клиента (п. 9) на той же 22.
5. **Пользователь `hqc` 10001:10001**, без домашнего каталога и shell. Хаб ничего не пишет
   на диск — проверено с `read_only: true` в compose, этот флаг стоит в примере RUNBOOK.
6. **`NO_COLOR=1` в `ENV`.** `tracing-subscriber` 0.3.23 по умолчанию пишет ANSI-цвета
   даже без TTY; `docker logs`/journald получали `\e[2m…`. Переменная поддерживается
   библиотекой, менять `main.rs` не пришлось. Не из списка задачи — добавлено после
   локального прогона.
7. **HEALTHCHECK нет** (как разрешает задача): `curl` в образ не тащил, `hqc-hub --health`
   не делал. Хаб без базы падает сразу (ретраев подключения нет), его перезапускает
   `restart: unless-stopped`; compose ждёт `pg_isready` базы через `depends_on`.
8. OCI-метки `source`, `revision`, `version` (+ `title`, `description`, `licenses`)
   задаются в Dockerfile через `ARG VERSION`/`REVISION`; в CI их же перекрывают метки
   `metadata-action` с правильными значениями.

## Workflow

9. **В `ci.yml` добавлен job `client`** (`npm ci`, `npm test`, `npm run build`). Раньше CI
   проверял только Rust, а образ теперь включает клиент: «образ после зелёного CI» без
   этого job'а не гарантировал бы, что клиент вообще собирается (сборка в Dockerfile
   упала бы уже в image.yml, после push в master).
10. **Триггеры**: `workflow_run` по `ci` (`completed`, `branches: [master]`), `push` тегов
    `v*`, `workflow_dispatch`. Для `workflow_run` job идёт только при
    `conclusion == success`, `event == push` и `head_repository == github.repository`:
    фильтр `branches` сравнивает только имя ветки, и PR из ветки `master` форка иначе тоже
    запустил бы сборку.
11. **Теги `v*` и ручной запуск тоже ждут зелёный CI**: первый шаг опрашивает
    `gh run list -w ci.yml -c <sha>` раз в 30 с до 30 минут; успешный `ci` на этом коммите —
    дальше, все завершены без успеха или таймаут — job падает. Так тег, запушенный вместе с
    коммитом, дождётся своего прогона `ci` (он идёт и на теги: `on: push` без фильтра).
    Нужен `permissions: actions: read`.
12. **Теги образа считаются явно**, а не `type=sha`/`type=ref`: под `workflow_run` контекст
    `metadata-action` — голова default-ветки, а не коммит, прошедший CI. Checkout тоже по
    `workflow_run.head_sha`. `master` ставится на `workflow_run` и на ручной запуск с ветки
    master; ручной запуск с другой ветки даёт только `sha-…`.
13. **Тег `vX.Y.Z` обязан совпадать с `workspace.package.version`** в `Cargo.toml`, иначе job
    падает до сборки: иначе образ `0.2.0` печатал бы `hqc-hub 0.1.0`. `latest` и `X.Y` —
    только для релизных `vX.Y.Z`, `vX.Y.Z-rc.N` получает лишь `X.Y.Z-rc.N` и `sha-…`.
14. После push — smoke-тест: `docker run --rm <образ>:sha-… --version` должен дать
    `hqc-hub <версия из Cargo.toml>`.
15. Платформа — только `linux/amd64`, как в задаче. Dockerfile архитектуру не фиксирует;
    arm64 добавляется строкой в `platforms:` (но под QEMU сборка Rust займёт десятки минут).

## Документация

16. RUNBOOK §1.8 — новый раздел; в §0, §1.2 (`HQC_HUB_LISTEN`), §1.3, §1.6, §1.7, §4 —
    только ссылки на него и одна поправка: в §0 «Node.js 20+» → «20.19+ для сборки, 22+ для
    тестов» (по `engines` в `package-lock.json`).
17. В примере compose два env-файла: `db.env` (`POSTGRES_*`) и `hub.env` (`HQC_*`), чтобы
    база не получала секреты хаба и наоборот. Пароль советуется hex — его не надо
    URL-экранировать в `HQC_DATABASE_URL`.
18. Сеть `edge` в примере — внешняя, на случай если cloudflared/Caddy живут в другом
    compose-проекте (их ставит другой агент, как именно — не знаю). Если в том же —
    вместо неё `default`. Вопрос к тому, кто разворачивает DMZ.
19. Команды обновления и отката (`pg_dump -Fc` через `docker compose exec -T`,
    `pg_restore --clean --if-exists` при остановленном хабе) прогнаны на локальном стенде:
    строка, удалённая после дампа, после восстановления вернулась, хаб стартовал.
