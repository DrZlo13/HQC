## Что подтвердилось про формат jsonl 2.1.308

- `claude -p "<промпт>"` и `--resume` (в том числе в stream-json-режиме адаптера) пишут **тот же**
  файл `<config>/projects/<encoded cwd>/<uuid>.jsonl`, `sessionId` и `cwd` одни; оба пишут
  `entrypoint: sdk-cli`. Прогон через настоящий плагин VS Code не делался — какой там
  `entrypoint` (ожидаемо `claude-vscode`), не проверено.
- uuid записей `user`/`assistant` основной цепочки совпадают в stream-json и jsonl, эхо
  `--replay-user-messages` несёт uuid записи промпта — как на 2.1.307. При `--resume` stream-json
  старую историю не повторяет: адаптер видит только записи своего процесса.
- Один блок контента — одна запись со своим `uuid`; блоки одного ответа модели связаны
  `message.id` и полем `apiBlockIndex`. Значит правило «блок `i > 0` — v5 от `"<uuid>/<i>"`»
  по-прежнему ни разу не сработало, но реализовано везде (`Event::id_from_claude_block`).
- `message.stop_reason` есть в jsonl у каждой записи ответа (`tool_use`, `end_turn`; у
  `thinking` и `text` последнего ответа оба `end_turn`), в stream-json — `null`. Зеркало берёт
  по нему `final` у `agent.message`.
- `thinking` в jsonl — пустой текст и `signature`. В stream-json адаптера в обоих прогонах такой
  записи не было (в jsonl на её месте `attachment` `thinking_drop` во втором ходе прогона а).
  Зеркало пустой `thinking` не эмитит и в детекции чужого писателя не считает — иначе
  собственная запись адаптера, которой нет в stream-json, выглядела бы чужой.
- `attachment` имеют `uuid` и стоят в цепочке `parentUuid` (промпт → attachments → ответ).
  Основную цепочку зеркало определяет по типу записи и `isSidechain`/`isMeta`, а не по
  `parentUuid`.
- Новые типы без `uuid`: `api-request-shape`, `atis-latch`, `mode`; `queue-operation`
  (`enqueue`/`dequeue`, у `enqueue` есть `content` с текстом промпта) перед каждым промптом.
- **`ai-title` не записан ни в одном прогоне**, в том числе с промптом аргументом (на 2.1.307 в
  `tool-call` был). Поэтому импортированные сессии в живом тесте получили «Сессия N». Остаётся
  **[проверить]** на сессии настоящего VS Code.

## Что расходится с §9 (было) и как решено

1. `workspace.list_candidates {}` — без `request_id`, в отличие от `fs.*`. Сделан `{request_id}`
   как у `fs.*` (ответ — `result` с тем же `id`).
2. «При регистрации воркер отдаёт `workspace.list_candidates`» — сделано по запросу:
   кандидаты нужны в момент импорта, а не при регистрации; хаб их не хранит.
3. `mirror.event {workspace_path, runtime_session_id, cwd, event}` — хабу не хватало двух
   вещей: заголовка (`ai-title` живёт в файле, событием §4 не является) и признака «пишут
   сейчас» для начального `locked_by` и 30 с тишины. Добавлены `title?` и `recent`; `recent`
   считает воркер по времени изменения файла на своих часах — часы хаба и воркера могут
   расходиться. Тишину для подхвата хаб считает от момента **получения** последнего
   `recent`-события (`vscode_active_at`).
4. «Неизвестный uuid файла становится новой сессией с `locked_by: vscode`» (§9.2) против
   «`none`, если в файл не писали 30 с» (§9.1): выбрано правило §9.1 для обоих — импорт старой
   сессии не делает её «занятой VS Code», живая запись (`recent`) делает.
5. «Пока hqc-процесс не запущен, любая такая запись переводит сессию в `vscode`» — уточнено:
   только запись с `recent`. Старые записи (импорт, догонка после простоя воркера) лок не
   трогают; иначе включение зеркала на тихой папке закрыло бы все её сессии.
6. В `mirror.event` воркер не знает `session_id` хаба и id автора: ставит nil, хаб заполняет.
7. Ни §4, ни §6 в этой задаче править было нельзя (параллельные T16/T17), поэтому описаны в §9:
   код `system` `session_released` (в таблицу §4), `409 vscode_active`, поле `hint` у
   `locked_vscode`, `GET /api/workers/{id}/candidates` (в §6 «позже»), `mirror_enabled` в `POST
   /api/workspaces`, `POST /takeover` для `locked_by: none`. **Перенести в §4/§6 при сведении.**
   Решено в T18: перенесено в §4, §5, §6 (SPEC 0.19, §23).

## Решения, которые стоит подтвердить

- **Опрос, а не notify** (§9.2): 2 с, без новой зависимости. На машине с тысячами транскриптов
  проход — `read_dir` + `stat` каждого файла; при первом проходе ещё чтение первых строк каждого
  файла ради `cwd` (дальше кэш). Не измерялось на большой папке.
- **Придержка 5 с** при живом процессе: запись в файл может опередить строку stdout. Пять секунд
  взяты с запасом; при долгом `tool_use` stdout приходит тем же моментом, что и запись.
- **Освобождение** очищает очередь ввода воркера, а хаб переводит `pending` вводы в `failed`
  (без отдельного `system`, видно по `delivery`). Альтернатива — держать их до подхвата; но это
  тихая очередь, которую §9.3 запрещает.
- **`locked_by` из `session.state`**: `vscode` воркера побеждает; `vscode` хаба не снимается
  `none` (остановка процесса) и `hqc` процесса, который хаб не запускал подхватом. Процесс
  сессии, которую хаб уже считает `vscode` (гонка: зеркало прислало `recent`-событие раньше,
  чем воркер отпустил), так и останется для хаба `vscode`, а воркер отпустит его сам по детекции.
- **Push** по событиям зеркала не шлётся вовсе (и живым ответам VS Code тоже): человек сейчас
  у той машины. Если нужно уведомлять о конце хода в VS Code — отдельное правило.
- Номер миграции `0006` может совпасть с T16/T17 — переименовать при слиянии.
  Решено в T18: `0008_mirror.sql` (`0006` — T17, `0007` — T16), SPEC 0.19.

## Открытые вопросы

1. **Сессии hqc в папке, где включили зеркало позже.** Если на workspace, где уже работали
   сессии hqc, включить зеркало (в T15 это возможно только созданием workspace, `PATCH` не
   сделан), первый проход импортирует их транскрипты: ответы агента дедуплицируются по
   `event_id`, а промпты — нет (у `user.message` хаба свой v7, у записи промпта — v5 от uuid). То
   же после падения воркера между записью адаптера в файл и проходом зеркала: реестр своих uuid
   в памяти. Варианты: воркер сообщает хабу соответствие «`event_id` ввода → uuid записи» по эху;
   или реестр на диске. Пока не сделано.
2. **Сессия, начатая в hqc и продолженная в VS Code** освобождается, только если её workspace под
   зеркалом. Для обычного workspace (без импорта) воркер чужого писателя не видит вовсе. Включать
   ли зеркало на всех workspace по умолчанию?
3. `PATCH /api/workspaces/{id}` с `mirror_enabled` («зеркало — позже» в §6) не сделан.
4. Один транскрипт, чей `cwd` менялся внутри сессии, привязывается по `cwd` первой записи.
5. Заголовок: `ai-title` в `-p` на 2.1.308 не пишется; брать ли заголовок из первого промпта
   (как делает VS Code в списке сессий)?
6. «Сессия N» для импорта нумеруется по проекту, как обычная; при импорте десятков сессий
   названия неинформативны — см. п. 5.
7. Подхват проверен с телефона только через клиент на мок-хабе и REST в живом тесте; живой
   прогон через UI на телефоне не делался.
