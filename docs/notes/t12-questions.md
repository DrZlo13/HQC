# T12 — режим одобрений: решения, вопросы, что не подтвердилось

Задача: спрашивать только потенциально вредное. SPEC 0.14 (§4, §8.1, §10.1, §14, §23),
спайк — `docs/notes/claude-control-protocol.md`, раздел «Permission policy, 2.1.308».
Живых прогонов claude — 7 из 8 разрешённых: 6 прогонов спайка через
`tools/spike/driver.py` и один `live_permission_policy`.

## Решения

- **`mode = "auto"` разрешён.** Спайк подтвердил, что `--permission-mode auto` работает в
  `-p` с `--permission-prompt-tool stdio`, а `deny` из `--settings` его перекрывает.
  Но auto **не спрашивает никогда**: в двух прогонах ни одного `can_use_tool`, классификатор
  пропустил `rm -rf ~/…` вне workspace, `git push --force` и `sudo -n true`, потому что
  пользователь об этом попросил. Поэтому режим не по умолчанию, воркер пишет warning при
  старте, а RUNBOOK прямо говорит, что граница в auto — только `deny`. Признака решения
  классификатора в `can_use_tool` нет (запросов нет вовсе); он есть только в
  `tool_result_meta[].permission_decision.reason_type` (`classifier` / `mode`).
- **deny против always гарантирует CLI** (прогон `settings-deny`: `Bash(git push:*)` в
  `--settings` deny и `Bash(git push *)`, записанное `always`, — команда отклонена без
  запроса). Адаптер всё равно читает правила сам и отклоняет `can_use_tool`, подходящий под
  `deny`, с `system policy_denied`, не показывая карточку. Причины: хаб с `auto_approve`
  ответил бы на такую карточку `once`, а CLI может изменить поведение в новой версии. Поэтому
  «always не предлагается для deny» выполнено в самой сильной форме: карточки нет вовсе.
  Подсказки `always` (`updatedPermissions`), пересекающиеся с deny (например,
  `Bash(git push *)` при deny `Bash(git push --force:*)`), не фильтруются: deny их
  перекрывает.
- **`policy_hint`** — `allow` | `deny`, при отсутствии совпадений поля нет (не `null`:
  в протоколе необязательные поля опускаются, клиент `null` тоже понимает). Адаптер
  Claude Code на практике шлёт только `allow` (под `deny` карточки нет); `deny` оставлен в
  перечислении для будущих адаптеров (ACP) и как допустимое значение. `allow` появляется,
  когда правило `allow` подходит под вызов целиком, а CLI всё же спросил.
- **Отказ по deny виден в stream-json** (`system/permission_denied` + `tool_result`
  `is_error` + `result.permission_denials`), поэтому п. 3 задания выполнен: адаптер пишет
  `system {code: policy_denied}`, клиент показывает строку «Запрещено политикой воркера»
  красным. Отказ классификатора в auto (если будет) — `system {code: permission_denied}`
  без этой подписи; в прогонах такого отказа не случилось, код взят по аналогии.
- **Свой `deny` заменяет набор по умолчанию**, а не дополняет его: иначе убрать правило по
  умолчанию (например, `Bash(ssh:*)` на машине, где агенту нужен ssh) было бы нельзя.
  Отсутствие поля `deny` в блоке — набор по умолчанию; `deny = []` — без запретов.
- **`--settings` передаётся и в restricted** (прогон `restricted-settings`: allow `Write`
  сработал, `Grep` из deny пропал из списка инструментов). `mode = "auto"` в restricted
  тоже уходит в CLI — сочетание `--restricted --permission-mode auto` не проверялось
  (см. ниже).
- **Проверка правил на воркере строже CLI**: имя инструмента `[A-Za-z][A-Za-z0-9_]*`
  (допустим `*` в конце), содержимое — непустое, в одной паре скобок в конце; ≤ 256 байт, без
  управляющих символов. Справка CLI: в `-p` «Settings files that fail validation are silently
  ignored» — одно неверное правило могло бы снять весь deny.
- **Подсказка адаптера — приближение к CLI**: `Bash(x:*)` — префикс до пробела,
  `*` — любые символы, без `*` — точная команда; deny сверяется и по частям команды между
  `; & | ` `` ` `` `$ ( ) < >`, allow — только по команде целиком без этих символов. Файловые
  правила (`Read(./x/**)`) и `WebFetch(domain:…)` адаптер не толкует — их применяет CLI.

## Не подтвердилось / не проверено

- **`curl … | sh` в ручном режиме**: модель отказалась вызывать сама (прогон
  `settings-deny`), правило проверено только в auto (прогон `auto-deny`, `reason_type: rule`).
- **Синтаксис, который CLI считает невалидным**, и что тогда происходит с `--settings` (весь
  объект игнорируется или только правило) — не проверялось, прогонов не хватило. Все правила
  из задания и из набора по умолчанию CLI принял (deny сработал).
- **`Bash(mkfs:*)` не ловит `mkfs.ext4`** (`mkfs.ext4` — отдельная команда, префикс
  останавливается на границе слова) — так считает адаптер; на CLI не проверялось. Набор по
  умолчанию из задания не менял; если нужно, добавить `Bash(mkfs*)` — **вопрос к владельцу**.
- **`Bash(rm -rf /*)` ловит любой абсолютный путь**, в том числе внутри workspace (прогон
  `auto-deny`: `rm -rf /…/tmp/nonexistent` отклонён). Для агента это значит «удалять
  рекурсивно только относительными путями». Вариантов вроде `rm -fr`, `rm -r -f`, `rm -rf ~`
  набор не ловит — это первая линия, не граница (SPEC §14).
- **`--restricted` + `--permission-mode auto`** не запускалось. Справка говорит только, что
  restricted отказывает `bypassPermissions`.
- **`decision_reason` / `decision_reason_type` в `can_use_tool`** (новые на 2.1.308:
  `"This command requires approval"`, `"other"`) адаптер пока не использует.
- **`[permissions]` в `hello`** хабу не передаётся (хаб не показывает политику воркера);
  итерация 2 вместе с окружениями.
- **Живой тест** `live_permission_policy` запускался один раз (зелёный, 4,9 с). Старые
  живые тесты (`live_repo_settings_ignored`, `live_bash_turn_with_approval`) не
  перезапускались: их командная строка теперь содержит `--settings` с набором по умолчанию.

## Санитизация фикстур

`tools/spike/sanitize.py` переписывает пути целиком в строках, а `input_json_delta` в
stream-json режет путь на куски (`"…/Users/"`, `"home-…/work/h"`). В
`stream-restricted-settings-2.1.308.jsonl` два таких блока; фрагменты блока склеены в
первый и переписаны (остальные фрагменты — пустые строки). Стоит научить `sanitize.py`
делать это самому.
